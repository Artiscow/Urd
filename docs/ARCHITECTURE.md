# Architecture

This document describes how Urd fits together. The data model - the contract everything builds on - is in [SCHEMA.md](SCHEMA.md). The reasoning behind the design choices is in [adr/](adr/).

## System overview

```
VISITOR                            EDITOR
   │                                  │
   ▼                                  ▼
yoursite.no ─────────────────► yoursite.no/admin
   │                                  │ GitHub login (OAuth)
   │  static files:                   ▼
   │  index.html                prebuilt editor (Svelte, compiled)
   │  assets/engine/*  ◄──┐           │
   │  content/**.json     │           │ draft in localStorage
   │  media/*             │           ▼
   │                      └── iframe preview: the REAL site,
   ▼                          draft pushed via postMessage
 the engine renders the site          │
 from content/ data                   │ «Publish»
                                      ▼
                          functions/api/github/* (Pages Functions)
                                      │ one commit via Git Data API
                                      ▼
                                GitHub repo  ──►  the host deploys (~1 min)
```

Two worlds, one repo:

- **The visitor site** is raw static files: `index.html` loads the hand-written engine (`assets/engine/`), which reads `content/site.json` + `content/pages/*.json` and builds the DOM. No build process, no framework.
- **Admin** (`admin/`) is a prebuilt Svelte app that is committed as static files. It edits the same JSON files, previews them through the real site in an iframe, and publishes via serverless functions.

## The engine (`template/assets/engine/`)

Hand-written, readable, dependency-free ES module JavaScript - never compiled ([ADR-0002](adr/0002-svelte-for-editor-readable-js-for-engine.md)). A module a visitor's page loads keeps short comments, at most 160 characters of prose on what the code does with its JSDoc tags whole, and the reasoning stands in its notes, [docs/engine-notes/](engine-notes/README.md)`<module>.md`, under the name each note explains, which the module's header names (`scripts/engine-notes.mjs`, `tests/engine-notes.test.mjs`). The ownership promise applies to what the visitor loads, and the editor's preview iframe loads exactly these files - preview fidelity is therefore structural, not something that has to be maintained.

Core parts:

- **`urd.js`** - entry point. Creates `window.Urd` with the registries, loads site + page, runs migration and render. The shell asks for `site.json` at once (`<link rel="preload" as="fetch" crossorigin>`, the same request the boot's fetch makes) and runs `theme-init.js` before its stylesheets, which a classic script after them would wait for. The engine's version is the name of the folder `urd.js` is served from (ADR-0013), so the boot reads no `urd.json`. A visitor's plugins load beside the page: the nav, the page and the footer wait for them only where they use a block, background or animation type the engine neither has registered nor holds as its own (`pageTypes` and `needsPlugins` in plugins.js), and a language pack's languages are registered for the editor alone, so a site in one of the engine's own languages never loads the pack module; a site in a pack's language reads its words through `initSiteLocale`. A visitor's footer joins the document once no block on the page is busy fetching its content (`aria-busy`, set by the collection, product, calendar and privacy blocks), within three seconds, so late content never pushes it down; the preview shows it at once.
- **`core-types.js`** - the engine's own block and background types, each with a loader that imports the module defining it ([ADR-0036](adr/0036-code-by-what-a-page-holds.md)), and beside it, in the same wave, the modules it imports that the boot does not load (`beside`), so none of them waits for the module that imports it, and the sheets of the block modules it draws with (`withSheets`: `blocks/<name>.css`, placed after base.css and the engine sheets in `BLOCK_SHEETS`' order by `placeInOrder` in sheets.js), so the type is defined once its sheets are in; tests/visitor-speed.test.mjs holds every loader to name them all. `reserveCoreTypes` holds every core id as the engine's in the registries as the boot starts (`reserve` in registry.js, which hands back the definer the engine defines them through), so a plugin's definition of one is refused whenever it comes, staged or direct; `loadCoreTypes` loads the types `pageTypes` reads, the nav's and the page's asked for side by side (the page's as soon as its file is read, with the first section's image layer pictures, `askLayerPictures` in urd.js), the nav, «Back to top» and the page then drawn in one task so they stand in one frame, and for a newer page file drawn in place (an old id such as `kalender` loading the type it stands for), and in the preview every type together with the section templates (`sections/presets.js`), before the preview reports ready. The modules stay out of the boot's static closure and the shells' preload list, and a module that fails leaves its blocks drawn as an unknown type. The nav's basket loads its drawer from `blocks/cart.js` as a nav with a basket is drawn. Beside the page's types, `prepareBlocks` readies what a core block on the page draws with beyond its module (`CORE_BLOCK_READY`, core ids only, never an old id a plugin may still draw, and never a block hidden on the visitor's screen), and the page is drawn once it is in, or after `READY_WAIT_MS` (half a second, as long as the loading bars wait) where it is not: a calendar's parser, design model, formats, links, stylesheet and the renderers its settings draw with, each design family's renderer with its own sheet (the plain views among them, `blocks/calendar-plain.js`, only where a calendar draws one), from `blocks/calendar-load.js`, which imports only the boot's own modules so it runs a wave before `blocks/calendar.js` and its imports are in. The event card (`blocks/calendar-card.js`) loads once the page is idle or at the first press that opens one, and the preview's editing of a calendar (`blocks/calendar-edit.js`: the words written in place, the help chip, the example events and the block menu's variants) loads with `preview-edit.js` and attaches itself to the block as it loads (`attachEditing`), so a visitor's page never loads it. Its feeds are asked for then too, never waited for: one request per feed shared by every calendar of it while it is on its way, and the readied request taken once by the first drawing of that feed (`takeReadied`). A calendar whose code is all in draws as the page's drawing ends, in the same task, so it stands in its own design in the page's first frame and its events fill it as they come.
- **`features.js`** - the boot's own features, each with a loader that imports the modules it draws with and its own sheet beside it ([ADR-0036](adr/0036-code-by-what-a-page-holds.md) decision 8): the basket in the menu (`shop.js`, `nav-cart.css`), contact details (`contact-model.js` and its profiles and checks), the footer (`footer.js`, `footer-model.js`, `footer.css`), the back-to-top button (`totop.js`, `totop.css`) and its own shape (`shape-model.js`, only where `toTop.shape` is set), pinned blocks (`sticky.js`, `sticky-model.js`), animations (`animations/core.js`, whose rules stay in base.css), section dividers (`divider-model.js`) and the collection drafts (`collections.js`). `siteFeatures` reads which the site holds on the page as site.json is read, and they are asked for beside the page file; `pageFeatures` reads which the page holds, asked for with its types in `pageReady`, so the page is drawn once both are in; the footer's is awaited only as the footer joins the page, and a newer page file's features are loaded as its types are. render.js, nav.js, footer.js and urd.js read a feature through `feature` as they draw, and draw without it on null, as if it were not set; a module the editor bundles never imports features.js, so the footer's contact parts and the head's organisation data (`footerContact`, `footerLegal`, `siteJsonLd`) take the contact model as an argument, and the back-to-top button's shape path (`toTopOf`, `toTopOutline`, `toTopClip`, `renderToTop`) the shape model. `reserveCoreAnimations` holds the core animations' ids as the engine's from the start, and `loadFeatures` defines them once their module is in. The preview loads every feature with every type. The feature sheets stand with the engine's other own sheets after base.css and before the block sheets (`ENGINE_SHEETS` and `afterEngineSheets` in sheets.js), in the order their rules stood in base.css; the newsletter form's checks (`footer-cta.js`) are asked for as the form is drawn and awaited as it is sent. The document designs' lists and normalisers stand in `doc-designs.js`, which the boot reads, apart from `doc-look.js`, which draws the documents.
- **`registry.js`** - shared registry factory. All extensible types use the same pattern:
  ```js
  Urd.blocks.define('text', { version, label, defaults, migrations, render, mount? });
  Urd.sections.definePreset('hero', { label, create });
  Urd.backgrounds.define('gradient', { version, label, defaults, migrations, render, pictures? });
  Urd.animations.define('fade-in', { version, label, defaults, migrations, apply });
  ```
  Plugins use the identical APIs - the core and plugins are equals. A background's `render(el, props, { first })` is told when it stands in the page's first section; one that declares `pictures: true` is drawn, below the first section of a visitor's page as it arrives, as its section comes within a screen of the viewport or before the page is printed (`renderBackgroundLayers` in render.js), and a later drawing draws it at once. The first image block of the first section is fetched at once with `fetchpriority="high"`, and every other image lazily; a text's height is measured by the push pass on the desktop and by the flow on the phone; and a calendar asks for its feed as soon as its parser is in, beside its other modules, and loads its design modules in one wave. While its feeds are on the way a calendar stands in its own design: a frame after its code is in it draws the design with the sample events into the height the loading state kept, their words and pictures hidden, out of reach behind a loading note (`urd-cal-wait` in blocks/calendar.css), still busy for the footer and never written into the structured data, so a feed already at hand is drawn without it, and so is a calendar whose calendar.css did not load (`loadStylesheet` resolves to whether a sheet loaded); the grey bars of the loading state in base.css show only once the code takes half a second. A calendar drawn again with the settings it was last drawn with (its section redrawn, the editor's drafts arriving, the phone's width crossed) starts from an inert copy of that drawing, the waiting one included, until its own is in (`copyLastDrawing`, the copy remembered in its turn), so it never blanks between two drawings.
- **`migrate.js`** - stepwise version lifting at load time. The most important file in Urd; see [ADR-0005](adr/0005-versioning-and-migration.md). Lifting happens in memory - the files on disk are only written at the next publish. Unknown type → neutral placeholder, data kept untouched. The load rule is `while (data.version < def.version) props = def.migrations[data.version++](props)`; the machinery (`lift`, `liftPageFile`, `liftSiteFile`) and the empty `migrations: {}` contracts of the core types are covered by the synthetic tests in `tests/migrate.test.mjs` and are the foundation the updater (ADR-0014) builds on. Until the first real format change after v1.0, schema validation (`npm run validate` + CI) is the active protection for the contract. The page migrations are listed in [SCHEMA.md](SCHEMA.md#the-page-migrations).
- **The stylesheets** - `assets/styles/base.css` holds what every visitor's page draws and the rules several block types share, stamped in every HTML shell, with one-line labels in place of prose, since every page loads it: the reasoning behind each rule stands in [STYLES.md](STYLES.md) under its selector, in the file's order; each block module's own rules stand in `blocks/<name>.css` beside it, with labels too and their reasoning in STYLES.md under the sheet, loaded with the module by its type's loader (core-types.js) and placed after base.css in the order the rules stood there, so a page loads the CSS of the types it holds alone, and a rule whose move would change which of two rules wins stays in base.css; the engine's `preview.css` holds the rules that need the preview's body class (the editing layer's handles, bars, menus and marks), loaded by the boot in the preview with `preview-edit.js`; and the calendar's sheets hold its views and designs: `blocks/calendar.css` the rules every calendar draws with and the ones several design families share, loaded with its modules by `blocks/calendar-load.js` before the page is drawn on a page that holds a calendar, and each design family's own rules in `blocks/calendar-<family>.css`, loaded with that family's renderer, each sheet placed in the order the rules stood in one sheet (`SHEETS`), so no rule meets another in a new order, while the calendar's loading state stays in `base.css` (`loadStylesheet` in sheets.js adds each once, where its caller places it). The engine's sheets are cached as the engine is (ADR-0013), so they need no stamp. A rule belongs to the preview when every selector needs the preview's body class (`.urd-preview`, which only the boot sets, in the preview, on the body or in a `:has` that asks for it) or names a class only the editing layer writes (by the modules `preview-edit.js` loads, and by none a visitor's page or the admin can load), and to the calendar when every selector is the calendar's; `tests/stylesheets.test.mjs` keeps each rule in its sheet, and keeps a preview rule from outranking a base rule by its later place alone (one with the same subject, specificity and a property).
- **`render.js`** - render loop: page → sections → background layers + blocks. Translates grid units (columns/rows) into CSS. Incremental: a single changed section is re-rendered on its own (used by the preview). On the desktop a section whose plain text would stand narrower than the readable floor (`READABLE_PX`, 140) is drawn in the row grid under the window width `phoneHandoff` (push-model.js) reckons from the texts' frames (a shrinking text at its smallest scale), the content width, the side margin, a side menu's column and the scrollbar's room (ADR-0034 decision 3), drawn as the phone draws it, its own words and its choice of blocks included (the addendum), its texts keeping the desktop's measure (`ctx.handoff` in blocks/text.js), marked `urd-handoff` with the width in `data-urd-handoff` (base.css draws its canvas, its gutter and its dividers as the phone's, and sticky.js pins its blocks as the phone does), left out of the push pass (`unwirePush`), and drawn again as a media query on that width changes (`watchHandoff`, one per section; in the editor the editor sends the section again, `urd-redraw-section`); in the editor's desktop view its canvas is inert, a selection in it ends, the seams, the marquee, the grid and guide overlays, the palette's and the paste's placing and a block's fit (`urd-fit-block` in urd.js) leave it be, its right-click menu greys what takes blocks or a desktop height, and its bar (`addHandoffBar` in preview-edit.js) says what is shown, with a help chip, and opens it in the phone view (`urd-edit-on-phone`, `lookOnPhone` in the editor's shell state). On mobile the blocks go into a row grid inside `.urd-canvas` (ADR-0019): `grid-template-columns: 5% repeat(8, minmax(0, 1fr)) 5%` and `grid-auto-rows: minmax(8px, auto)`, with `MOBILE_ROW = 8` and `PHONE_COLUMNS = 8` exported from `migrate.js`; a block without cells spans the whole row (`grid-column: 1 / -1`), 90 % wide and centred. A placement with cells (`col` and `cols`, `phoneCells` in migrate.js) stands in those columns: flowing blocks one after another in the same cells are drawn in one `.urd-cell`, the grid item `phoneCellCss` places with half the space between blocks on its inner edges, so a column of blocks and a block beside it share a line by the sparse auto-placement; in the cell a block fills its width, a block whose size is its frame (`FIT_BY_WIDTH`) takes its desktop shape as `aspect-ratio`, and a cell holding words narrower than about 140 px stands across the row by the floor's media rules in base.css (`urd-cell-words`), where the section's «Force readable text» on the phone is on (`forcesReadable`, ADR-0034; off, render.js marks the flow `data-urd-free-words` and the rules stand aside). A drop, the key carry or a handle that would give words fewer columns than the floor allows greys the dragged block and posts nothing, telling the editor, whose notice line says why (`phoneTooNarrow`, `showTooNarrow` in preview-edit.js, `urd-too-narrow`); on the desktop the same setting gives a text block's paragraphs a 75-character measure (blocks/text.js `data-urd-measure`) and stops its width handle at 140 px; a text's long words are hyphenated or kept whole by the theme's `theme.words` (`wordsVars` in theme.js, as CSS variables in theme.css) or the block's own `props.words`, read by a text block's words (`data-urd-text`, base.css) in the editor and on the published page alike, both ways written outright so a draft's choice wins over a published theme.css; the measure is a plain text's, each paragraph aligned by the text or by itself. A block pinned in cells is a grid item of its own on its rows, and a block pinned on the phone while the page scrolls hands its columns to its slot, the holder placing it over the slot's own width. The presets that suggest a phone layout are reckoned in the editor-only phone-layouts.js (`phoneLayouts`, those that fit first, `phoneLayoutChange`, a unit's cells and for «Alternate sides» the order through `settle`, and `phoneLayoutSketch`, the small drawing), with the site's own layouts after them (`site.phoneLayouts`, each rows of the two columns, `full`, `two`, `big-left` or `big-right`, repeated over the section's units in the phone's order; `ownLayoutOf`, offered as `own:<id>` and drawn and applied by the same two functions with the layout itself in place of an id; composed and kept from the section's phone rows): the phone view's section bar opens them in the picker «Change layout» opens on the desktop (`toggleLayoutPicker`, `urd-phone-layout`), and the section's phone rows draw them as cards. After them stand «Same width», `phoneSameWidths` over the lines `phoneLines` reckons as the row grid places them, and «Same height», measured in the phone view (`phoneSameHeights` in preview-edit.js, asked for by `urd-phone-same-height` and posted as `urd-phone-layout` with the heights); a preset asks for the heights after it, and they join its undo step (`<key>:then` in history-model.js joinsLast). Flow blocks are auto-placed (sparse) in the reading order of `stackOrder` (phone-order.js): the section's `phoneOrder` reads them top first by their desktop top (`mobileOrder` overriding the key) or, Left or Right first, column by column, where bands of blocks whose heights overlap are split into columns of blocks whose widths overlap and bands whose columns line up one to one stand as one grid; the section's `phoneStacks` make units of blocks that read as one, each standing where the first of its blocks in the rule's order stands; each block's `phonePlace` then puts it, or the stack it heads, before or after another block or stack, and a `phoneList` holds a custom order as listed, a block missing from it joining after the block before it; the phone view's numbers (`.urd-phone-num`, preview-edit.js) show the order. The owner's moves in it (the arrows on a block's bar, Alt with the arrow keys, the Phone panel's list and the drag on the phone canvas) are reckoned in phone-moves.js, which the visitor never loads: the order is drawn as a tree one level deep (`phoneTree`), and a move is a new order of that tree settled into the section's data (`settle`), the stacks as they stand and either the custom order as listed or the exception that brings the moved block or stack there, a block placed against the moved one following it unless the move lands right beside it on the far side of the block it names, where it loses its exception; a block dragged out of a group, or taken out by «Ungroup» (`phoneUngroup`, from the Phone panel's row menu or the block's menu on the canvas), is taken out of the rule's column it stands in, kept in the section's `phoneLoose`, so `phoneParts` no longer gathers it there and the owner's stack it leaves cannot fall back into a column; a flowing block dragged on the phone canvas (`flowDrag` in preview-edit.js, the eight columns drawn as `.urd-phone-cells` and the landing as `.urd-phone-land`) lands where `phoneDropAt` reads the pointer over the other units, before or after one or the line of units side by side it stands in, or at the edge of one nearest the pointer, the unit cut in thirds across: beside it, the two sharing the room of its line around it half each (on a full line its own columns, nothing else moving), or above or below it in its column as a stack, a unit across the row included (the preview outlining the stack, `.urd-phone-stackmark`), or along the block's own line (`here`); a block placed in a gap, in empty room or along its line keeps its own width at the pointer (`placeAt`, the drop's `x` in columns and `fine` with Alt), and the rules are tested row by row against the Phone Drop Map of 14 November 2026 (tests/phone-order.test.mjs) (on the block under the pointer, in a unit of several; a block alone across the row before or after it), the room a line leaves beside a unit taking the columns free there (`free`), its own place held at its size (`.urd-phone-hold`) and landing nowhere, and `phoneDropChange` turns that into the move with the cells it gives, beside a unit half each or the columns its line leaves free, and the unit's own in a stack, posted as `urd-phone-order`; while the block is held over a place, `phonePreview` draws the section with the change written in (`phoneChangeApplied`) out of sight beside it, as a copy to measure (`renderSection`'s `measure`: drawn as the preview draws its blocks, without the editing layer and without animations), measures each block's place there, and the shown blocks glide there by transform, the dragged block's place a dashed box (`.urd-phone-landing`), the drop read on the units as shown, and a gap on the units as the drag began, since the preview opens gaps of its own, the result held over the landing box and the gap right above and below it; the same block lifted with Alt and an arrow key (`phoneCarry`) walks the places `phoneKeyDrops` lists, above and below each unit's first and last block, Left and Right beside that unit, shown by the same preview with the block itself gliding there (`.urd-phone-carried`), Enter posting the change and Escape, a press or the selection leaving it putting the section back; its handles on all four edges and corners (`cellResize`, by the edge dragged) set the cells' span from either side, a stack's blocks together and a cell with words never narrower than the words floor draws at the window's width (`leastWordsCols`), and its own height on the phone (`frames.mobile.height`, which `mobilePlacementToCss` draws as a least height for a block with words and the height of any other, a picture then giving up its shape), in the row grid's steps or lined up with the bottom of a block beside it (`phoneHeightSnap`), sent as `heights` in the change beside `cells`; a block pinned to rows is sized by the same edges on its rows (`mobileDrag`); and the pin on its bar (`pinOnPhone`) pins it to the rows it stands on, in its cells where it has some; a block that is neither text nor auto-growing spans `ceil((desktop.h + gap) / 8)` rows, the gap under it held at most at the standard 16 px, while text and auto-growing blocks span one row and take their natural height. The gap under each flow block is its margin, `--urd-mobile-gap` from `mobileGapOf` in `migrate.js` (the section's `size.mobileGap`, the site's `layout.mobileGap` or 16), and a gap larger than 16 grows the row tracks, as a text block's margin does, so blocks placed by hand keep their distance. Pinned blocks get `grid-row: row / span rows`, `width: w%` and `margin-left: x%` of the surface, plus `z` and `rot`. A block that shrinks on the phone (`shrinksOnPhone`: `fit: "shrink"` on any type but image, video, shape and icon, which follow their frame, and the calendar, which draws its phone view) keeps the lines it has at the design width: its content is zoomed by its width in the row grid over its width at the design width (`phoneFitZoom` in push-model.js, `zoomOnPhone` in render.js), down to `fitMin`, and a `ResizeObserver` zooms it again in the next frame as that width changes, its loading reserve with it. A block with a size of the phone's own (`phoneSize`, 0.7.36.2, ADR-0019 decision 1) is drawn there at that size in place of `size`: `phoneSized` in push-model.js gives the phone's paths in render.js (`zoomOnPhone`, the loading reserve, `isNarrowBlock`) the block with its size swapped, and the desktop's paths read `size` as before. A block pinned on the phone (`sticky.phone`, `pinsOnPhone` in sticky-model.js) keeps a slot of its size in the grid (`.urd-stick-slot`) and stands in a holder (`.urd-stick`, `position: sticky` below `--urd-scroll-clear`) in a layer as large as the grid (`.urd-stick-layer`, at the desktop pinning's level), since a grid item may stick only inside its own grid area; a release at a later section (`until`) stretches the layer down to that section's foot, so the holder sticks across the sections between; a pinning group shares one holder spanning its slots (`stuckBox`), and a `ResizeObserver` on the blocks, the grid and the release section places the holder again in the next frame (`stickOnPhone` and `placeStuck` in render.js). A phone drag of such a block takes it back into the grid and draws the section again after the drop. On the phone a block reads its own words where it has some ([ADR-0033](adr/0033-words-of-its-own-on-the-phone.md)): `propsForViewport` in push-model.js merges the words its type holds (`PHONE_WORDS`) from its `phoneProps` into the props `renderBlock` draws in the mobile viewport, in the phone view and on the published page at phone width alike; the text block is written in place in the phone view too, as are the quote, the statistic's label, the audio player's title and the countdown's words for the end, their `urd-edit` carrying `phone: true`, which the editor's `handleEdit` keeps in `phoneProps` (`phoneWordsChange`, the typed words that differ from the desktop's) without writing the desktop's props or frame, the canvas marking such a block (`.urd-phone-words`); a block of several fields hands back every field as it stands on the page, the editor hands the words it keeps, the desktop's and the phone's own, to the page's copy of the section without drawing it again (`urd-block-words`), so a later drawing such as a switch of view reads them, and in the editor a block is given the phone's own words in its context (`ctx.phoneWords`), so a field emptied there stands to be written in again. `stackOrder`, `phoneStep`, `phoneLand`, `mobilePlacementToCss`, `shrinksOnPhone`, `phoneFitZoom`, `pinsOnPhone`, `stuckBox` and `propsForViewport` are pure functions.
- **`theme.js`** - maps `theme.tokens` from `site.json` to CSS variables (`--urd-color-bg`, `--urd-font-heading`, …). When the theme has no `accent-text` token, `buildThemeCss` writes the effective value (the background colour) as the fallback in `:root` and, behind `@supports (color: contrast-color(#000))`, lets the browser pick black or white against the accent with `contrast-color()`; an owner-set token is written as it is, and «Auto» in the Theme panel removes it.
- **`sanitize.js`** - the rich-text allowlist (`RICH_TEXT`, listed in [SCHEMA.md](SCHEMA.md#rich-text)): a text block, an FAQ answer, a collection or product entry's title and text and the calendar's own words are parsed in an inert document and rebuilt from it (`setRichHtml`), and a paste into a text in the canvas goes through the same list (`cleanRichHtml`, preview-edit.js), with Ctrl+Shift+V pasting the words alone. A calendar feed's own HTML goes through a narrower list of its own (`safeHtmlFragment`).
- **The SVG check** (`svgProblem` in `imageTools.js`): an SVG is read tag by tag with its references decoded, and refused at upload, from a CSV file and at publishing when it holds a script, a handler, a script address, an animation of a link or a declaration of its own; the publishing guard holds the same function (`functions/_lib/svg-check.js`, its text held equal by a test) and refuses such a file in media/ (`svgNotAllowed`).
- **`hint.js`** - the help chip of ADR-0008: `attachHint(host, { title, lines })` attaches the «?» chip to a block or section host and owns the help card; on a block with a toolbar the chip is the bar's last tool (a chip drawn before the bar is taken in by `enhanceBlock` in preview-edit.js), and the chip and the card are styled by hint.js itself. Plugins import the same helper from the stable path `/assets/urd/hint.js` (ADR-0013) and call it only when `ctx.preview` is true.
- **`i18n.js`** - the two dictionaries of ADR-0012. The admin language is stored in localStorage under `urd-admin-lang`, shared by the admin and the preview iframe (same origin). `locales/site/nb.js` is imported statically (preloaded); other site languages are dynamically imported in `boot()` after site.json is read, on top of a FRESH copy of the base, and that import is deliberately invisible to the modulepreload contract. `boot()` sets `document.documentElement.lang` (the shells hardcode `no` only as the pre-JS default). The editor's main.js imports the admin dictionary from the engine's `locales/admin/<lang>.js` at runtime before mount, and the preview's canvas chrome does the same lookup itself (`initAdminLocale`: the bokmål base and the language's own words read together); a language switch is a reload because of the roughly 900 `ta()` call sites. The language-pack lookup lives in `language-packs.js`, deliberately OUTSIDE the engine's static import closure: it is fetched only when a language the core does not have is asked for.
- **`search-langs.js`** - search in every language (0.7.10.5): the editor's searches (the element menu, the Blocks panel, the command palette, the Urd settings, the link editor's spots and the design, icon and glyph pickers) and the canvas's block menu and section gallery load every built-in admin dictionary on the first query, from the same paths `initAdminLocale` uses, and the admin dictionaries of the enabled language packs through `language-packs.js`; a word typed in any of these languages also matches the labels it stands for in the admin language, whatever the admin and the site are set to. Searches over the owner's own words (pages, entries, files) match them as typed. The matching over the index is pure and node-tested; the menus keep matching the words they show, with the hits through another language ranked after the hits as typed.

### The navigation bar's sizing (ADR-0023)

The size preset `nav.style.size` (sm/md/lg/xl) is a `urd-nav-size-*` class on the nav that sets `--urd-nav-size-pad` and a font size in rem. Free values override it through inline custom properties on the nav element: `nav.style.padY` as `--urd-nav-pad-y` and `nav.style.textSize` as an inline `font-size`. The chain in `base.css` is `--urd-nav-base-pad: var(--urd-nav-pad-y, var(--urd-nav-size-pad, 0.9rem))`, so a stored padY wins over the preset and the preset over the fallback. The floating pill multiplies the preset padding by 0.67 by overriding `--urd-nav-base-pad`, never the derived `--urd-nav-pad`, so an explicit padY stays raw in every variant. With an image logo the bar's height has a floor of 36 px whatever padY says, because the logo's margin calibration contributes a constant.

The side padding is `--urd-nav-px`, which defaults to the fluid `clamp(1rem, 4vw, 2.5rem)` and is set directly by `nav.style.padX`; the mobile panel and the side-to-bar fallback read the same variable. With `nav.style.inset` the side padding on desktop becomes `max(padX, the desktop gutter, (100% - canvas width) / 2)`, resolved against the body-wide host, the same reference the canvas uses (`--urd-canvas-w` and `--urd-canvas-gutter-desktop`, set on `<html>` by `applySiteLayout`). The floating pill is `min(1100px, 100% - 2rem)` by default; `nav.style.pillWidth` replaces the 1100 px with a px value or, for the string `content`, with the content width less the desktop gutters, and the override is suppressed at the mobile breakpoint, where the pill keeps `100% - 2rem`.

The mobile and compact overrides are chosen by the pure helper `navSizeVars(style, logo, { mobile })` in `nav-model.js` and written inline by `nav.js` at render time. The compact factor `nav.style.shrinkTo` lives inline on the nav element as `--urd-nav-shrink-to` while the host carries the state class, and the compact rule targets the nav: `.urd-nav-compact .urd-nav { --urd-nav-shrink: var(--urd-nav-shrink-to, 0.5) }` (the default factor is 0.5). The logo height is written as `--urd-logo-base` on the img, and the CSS derives the rendered size from it so the shrink-logo rule can scale it with the padding. Border and shadow are allowlisted classes: `urd-nav-border-<side>` with the width and colour as custom properties, and `urd-nav-shadow-<strength>` (soft/strong). The side column keeps its own padding, `1.2rem 1rem`; `padY` and `padX` do not touch it. The editor's `setNavStyle` deletes a key when it is set to undefined, and an emptied `mobile` object is removed, so defaults are never written to the file.

### Desktop sizing: the push pass, the fit and the gestures

The decisions are in [ADR-0024](adr/0024-content-push-on-the-desktop-canvas.md) (content push) and [ADR-0025](adr/0025-the-sizing-model.md) (the sizing model); this is how they are built. The pure parts are in `push-model.js` (`pushLayout`, `fitMoves`, `followsContent`, `heightAlign`, the type sets) and tested in node; the measuring parts are in `render.js` and `preview-edit.js`.

- **The push pass** (`applyPush` in render.js) runs for every desktop section one animation frame after the blocks' own measurements, and again on every `ResizeObserver` notification from a block or its content (fonts, images, feeds, width changes), deduplicated to one pass per frame per section. It works in phases, so the reads of most blocks share one layout rather than one each (a block that follows its content, or holds the editor's own parts, measures with writes of its own): it reads the canvas's width, writes every block's frame height and shrink (`fitContent`), then measures every block, then writes the heights; for each block it measures the height the content needs as `max(offsetHeight, scrollHeight)` of the content children with the box at the design height (so overflowing text counts; the editing handles never count, and a zoomed child is converted to the block's px), and asks `pushLayout` for the shifts with the gap thresholds `PUSH_GAP_MAX` (70 px) and `PUSH_GAP_MIN` (10 px), for the blocks that share more than `PUSH_ACROSS_MIN` (0.1 %) of a grown block's width; `frameToCss` writes the design position from `frames.desktop`, the pass writes the shifts as `style.top` and `data-urd-shift`, the drawn height as `data-urd-drawn`, and a pass without growth writes the design positions back. The measurement is two-way: the box grows with its content and returns to the design height when the content fits again. A block pinned by sticky.js keeps its stash up to date instead of its inline top, so a release lands right. The shrink of `fit: "shrink"` is a bisection between full size and `fitMin`, run before the box height is measured, so the content is zoomed only as much as the design height needs; for image, video, shape and icon the same fields are a floor on the frame's width (`fitFloorPx`): the frame follows the canvas in percent but never gets narrower than the floor times its design width, capped at the canvas's right edge. An image block is measured at its frame's height and never grows from its content, since a zoomed or turned picture overflows its clipping frame without being content to make room for. A block that follows its content (`data-urd-height="content"`) is measured by `hugHeight`: its natural height when it is drawn at its content, or 0 to keep the frame while it is still loading (`aria-busy`). Such a block is observed through its content children alone, since a box the observer watches and the pass resizes in its own callback would come back as a notification it cannot deliver in the same frame.
- **Editor-only parts never push.** The image adders, the «+ Product» card, the placeholders of empty fields and the calendar's notes about removed lines are drawn in the preview but are not on the page; `EDITOR_ONLY` in render.js lists them, base.css hides the same list under `.urd-fit-measure`, and a test holds the two equal. The pass draws a block with them but measures its growth as a visitor sees it (`asVisitor`, `visitorHeights`), so the editor's section heights are the published page's.
- **The section line.** `writePush` sets the section's inline min-height from `data-urd-min-height` (the section's own height, or the blocks' extent when it has none, kept there so the section returns to it when the growth is gone) and counts a block towards the section only while its design bottom is inside that height. In the preview (`_urdPushPreview`, set by `wirePush`) a section with a height of its own is never raised by growth; on the published page it is raised to the pushed bottom plus `PUSH_SECTION_PAD` (24 px). A section without a height of its own follows every block in both.
- **The seam grip (section-size.js, 0.7.0.87).** Each bar on a seam between two sections holds a grip (`seamGrip` in preview-edit.js), and the gallery of section templates the section toolbar's «New section» opens on the seam below it (`openSectionGalleryBelow`); its «New section» chip stands only on an empty page. The toolbar's «New block» opens the block menu under itself (`toggleBlockMenuFrom`). The grip is a pill that grows the section above as it is dragged down and the section below at its top as it is dragged up, never shrinking either, and a tab above and below it that shrinks the section it stands in. `seamDrag` holds the rules: grid steps unless Ctrl or Cmd is held, a shrink that stops at the section's lowest element (above) or where its topmost element meets its top (below) unless Alt is held, and three grid steps as the least height. A section that changes at its top takes its blocks with it and the page scrolls by as much, so the content stands still; the drag ends in one `urd-section-size`, with the blocks' moves for the section below. The first seam has only a section below and the last only one above, so they carry one tab.
- **Snapping (snap-model.js, 0.7.10).** A dragged block snaps to the edges and centres of its neighbours, to the content surface's quarters and midline, and to the gaps its neighbours keep between them (equal-gap snapping, the tldraw rule), within eight screen px whatever the preview's zoom (`snapTolerance` from `--urd-chrome-scale`, the Excalidraw rule). The targets come from the section the block came from and the section its centre is held over, measured in the source canvas's px, and the lines are drawn there: a line between the block and a neighbour spans the two, a line of the content surface reaches a little past the block with its share in a label, every line ends in a dot, and an equal gap is a band with its size. The grid is counted out from the content's middle (`gridLine`, 0.7.34): a line on its centre and the part cell left over split equally between the two edges, so a position snaps to a line from the middle and a width to whole cells; preview.css draws it the same way in the look kept per browser (`urd-grid-look`, `GRID_LOOKS`: quiet lines, dots, or columns at rest with the grid only in a drag), and the guide lines carry their share. The grid overlay stands on every section while a block is moved, since a block released with its whole box outside its own section moves to the section under its centre; a block that still overlaps its own section stays and lies over the neighbour (ADR-0025 decision 8). Ctrl or Cmd turns the grid and the guides off for the drag; Shift holds a move to one axis, and on a resize of a block whose size is its frame it keeps the ratio.
- **The pass stands still under a gesture.** `suspendPush`/`resumePush` sit beside `suspendSticky`/`resumeSticky` in preview-edit.js. While suspended the pass touches nothing; the drag draws its block at the frame plus the block's own shift (`pushShiftOf`, read from `data-urd-shift`) while the frame it writes stays free of the shift, and the pass runs again from the new frames on release. Smart guides and the marquee measure `offsetTop`, which is the shown position, and the guide comparison adds the dragged block's shift so it aligns what the owner sees. The guides snap from the frame under the pointer before the grid's step, so a line between two steps can be reached; an axis with no line in reach keeps the grid's place, the content surface's midlines win over a nearer line (`prefer` in `edgeSnap`), and every line the placed box stands on is drawn (`alignedLines`).
- **The layer order (layer-order.js, 0.7.30.6).** A block goes in front of its section's other blocks or behind them all, never one step, and a z never below 1: the canvas's arrows, its right-click menu, Ctrl+Shift with the arrows and the element menu's actions all move it through `layerChanges`.
- **The row grid that was not taken.** A desktop row grid (the alternative ADR-0024 rejected) would rewrite about twenty files (`frameToCss` and the desktop branch of render.js, base.css, sticky.js, twelve sites in preview-edit.js, place.js, section-size.js, selection.js, section-layouts.js, the 112 hand-written frames in sections/presets.js, templates-model.js, preset-thumb.js, migrate.js) and ten test files, and break several invariants: sticky.js reads a block's `y` from `style.top` and writes it back when parked, `.urd-canvas` must leave `position: absolute` (ADR-0018), `y` may be negative for blocks hanging above the section, sections never clip while a grid reserves space for every item, 100 of the 112 preset `y` and `h` values are not aligned to a row step, `mobileOrder` and the presets' card order use desktop `y` as a pixel-scale key, and a row step would have to be a model constant rather than `grid.size`.
- **Typing.** The text block's input listener measures its words with the box at its own height and asks `typedFrames` in push-model.js for the section's frames: the text at the height its words need, rounded up to the grid step and never below the height before the typing, and the blocks below moved by the push rules from where they stood then, all posted as `urd-move` in the typing's undo step. text.js keeps the frames from before the typing per block while the section's frames are the ones the typing wrote last; any other change (a gesture, a fit, an undo) starts the typing afresh from the frames as they stand.
- **The fit.** After an edit of a block that follows its content, the editor (`fitBlockSoon` in state/page.svelte.js, debounced per block with a sequence number so only the latest answer counts) posts `urd-fit-block`; the preview measures the block at rest as a visitor sees it, three times to catch a design drawn by a module loaded on demand or a feed answering late, and answers with `urd-grow` carrying `fit: true`. The editor writes the height into `frames.desktop.h`, moves the blocks below by `fitMoves` (the push rules applied to the growth, so the data takes over what the pass drew) and sends `urd-frames`; the preview puts the frames into the section the pass holds (`updateFrames`) without drawing it again, so a caret in the block's text survives a fit that follows typing. The measure leaves out the unfolded part of open `<details>` (`unfoldedHeight`): an FAQ answer or a calendar fold a visitor opened is view state.
- **A new block's box (add-fit.js, ADR-0025 decision 1).** A block added from «+ New block», the Blocks panel or the palette (`insertBlock` with `fit` in state/blocks.svelte.js, and `urd-add-block` with `fit` from the preview's `placeBlock`) asks the preview for its box fitted to what it draws (`urd-fit-new`, with the width it was added at), before it sends the section. `fitNewBlock` and `beginNewFit` in preview-edit.js draw the block hidden and measure it as a visitor sees it before the next paint; a calendar or the privacy page (`DRAWS_LATE`) in the frame after it says it has drawn (the event `urd-drawn` on the block, from the calendar's `settle` and the privacy page's draw), and a plugin's block that asks to be fitted (`fitWhenAdded`, `pluginFits`) every 120 ms until two measures agree and nothing in it is loading. In the editor's preview the calendar loads what it draws with, every design's renderer among it, once the editor is idle (`warmCalendar` in blocks/calendar-edit.js). The fit is the narrowest width (`narrowestWidth`, by halving, no narrower than `addedFloor`, which keeps a block with a phone design added at `NARROW_PX` or wider above it) at which its words stand on no more lines, nothing in it spills sideways and it grows no taller, and the height its content needs there; a calendar fitted below `NARROW_PX` stays hidden two frames more, as it turns to its narrow layouts in place, and is measured again in them. The frame is drawn on the block (`drawFrame`, the section's height following), the block shown, and the fit sent once with `urd-new-fitted` (no size where none was taken), so the block never changes size once it is seen. The editor writes it with `fittedFrame` (the horizontal centre kept) while the add is the last step and the block stands as added, so one undo takes both away, and draws nothing again; a fit it no longer takes is answered by drawing the section from the draft, and the fit of the height of a block that follows its content runs once the answer has come. The kinds whose box is what they draw (`KEEPS_ADDED_SIZE`, and a text in a box) are not fitted, nor a duplicate or a paste.
- **A block added in the phone view (ADR-0019).** Every way to add in the phone view carries the phone's place in its message (`phone: {drop}`, `phoneAdd` in preview-edit.js, on `urd-add-block`, `urd-add-blocks`, `urd-request-block` and `urd-calendar-designs`): the drop a block let go at the point makes (`phoneDropAtPoint`, read on the units' boxes by `phoneUnitBoxes` as a drag reads them, a point beside a block with less than a column of room landing after its line), the bar's «New block» first in the section (`phoneDropFirst`), the Blocks panel in the middle of the view between the lines (`phoneDropMid`), a duplicate after its block's line (`phoneAfterLine`), and a paste from the section's menu at its point. The editor (`phoneOf`, `addOnPhone` in state/blocks.svelte.js) writes the blocks with `phoneAdded` in phone-moves.js in the step that adds them, and fits none of them.
- **The gestures.** At the first move of a drag, a resize, an arrow key, align or distribute, `settleFrames` in preview-edit.js settles the frames of the blocks under the gesture to the boxes the pass draws for them (a block that follows its content takes its resting height, any other block its growth) and moves the blocks below by `fitMovesAll`, writing into the section the pass and the editing layer hold; the settled frames go to the editor as `urd-move` messages in the gesture's undo step (`postSettled`), and a gesture that changes nothing calls the settle's `undo`. While a gesture runs the pass is suspended (`suspendPush`/`resumePush`) and `pushPreview` draws the push as it will be on release from the frames under the pointer; the blocks being moved are left out of the section height, a resize keeps its block in it. The lower handle of a block that follows its content changes the width only, and a pull up or down shows the stop bar (`.urd-edit-stop`) at the content's edge; a fit that lands during the drag (`urd-frames` into the same block) wins over the height the drag began with. A block given its own height (`height.mode: "own"`) is no longer `followsContent`, so every path above treats it as a box. A video given a shape is `followsContent` (`keepsShape`): its content is a box of that shape at its width, and the fit's answer for it is replaced by `shapeHeight` at the design width, since the preview's content surface can be narrower than the design width and a measure there would shrink the frame at every change of shape.
- **The content in a box with its own height.** `heightAlign` reads the block's `height.align`, render.js writes it as `data-urd-align` on the block in both the desktop and the mobile branch, and base.css lays such a block out as a grid of one row: the content keeps its own height and moves to the middle or the bottom, or takes the row with stretch, which each type's own layout then fills (the figure centred, the countdown's units grown, a quote's card filled, the plain list and card calendar views spreading their rows and cards under the finding tools and over the subscribe row, with the calendar root as a flex column for that case). The editing handles and badges are absolutely placed and stay out of the row.
- **The block's own width.** The blocks with columns, cards or a layout that changes when the box is narrow (`FOLLOWS_WIDTH`) are marked `data-urd-width="own"` and are size containers named `urd-block` in base.css; other blocks are not, since a container box would hold a fixed-position descendant, which a plugin block may have. A rule that asks the block's width is a container query, and the window's media query it replaces stays beside it behind `@supports not (container-type: inline-size)` with the same declarations; a test holds the two equal. The calendar's narrow layouts are a different DOM (dots that open the day, stacked days) and are chosen in script by the block's width, read from a zero-height ruler beside the calendar so the pass's changes to the block's height never reach the observer. Galleries and product cards write a wide and a narrow column count and let the container query pick.
- **The map.** The map's box is its frame: `.urd-map` is a grid of the iframe row and the «Larger map» line, and the iframe fills what the frame leaves. The height setting it had until page schemaVersion 4 is lifted into the frame by `liftMapHeights` in migrate.js (the page migration 4 → 5, and template insertion), which gives the frame the height the map showed and moves the blocks below as a fit would.

## The editor (`editor/` → `template/admin/assets/`)

Written in Svelte 5 + Vite in the main Urd repo. At release it is built to static files in `template/admin/assets/` which are **committed** - associations that clone the template get a ready-made editor and never touch npm. The source code is open here; the compiled files in cloned repos are its product.

Key mechanisms (patterns validated in ApeironLF):

- **Draft:** all editing is written to `localStorage` once the changes pause (`lib/draftStore.js`: every store with a change waiting is written together 250 ms after the last change and at most 2 s after the first, and `flushDrafts` writes them at once before an undo, a redo or a jump in the list of steps, the undo history's keep, a publish and again as it lands, Discard drafts, a page switch, the saved drafts, the draft view («Test the payment»), a new store for a key and the page going; a store's `saveNow` writes at once). A «baseline» (the published state) is compared against the draft; if they are equal, the draft is removed - this keeps the «unpublished changes» marker always honest, a change still waiting counting as a draft until it is written. A deleted draft is removed with `dropDraft`, which also lets go of its store's waiting write.
- **Undo history:** each step holds the state before the change as text, an unpublished picture's data address in it a token (`lib/history-media.js`), the address kept once in a table however many steps hold it; a token comes from the picture's own content, so a kept history finds its pictures in the next session. The history is kept over a reload in IndexedDB (`lib/history-store.js`) as an index of the steps, a record per step and a record per picture, a keep writing only what is new and the newest step, and deleting what no step holds; a mark in `localStorage` holds hashes of the state the steps lead to, with its pictures as tokens, so a session takes up the kept steps only when the drafts are the ones they were kept with.
- **Startup:** the editor bundle is minified in full (`rolldownOptions.output.minify` in vite.config.js). `init()` in state/shell.svelte.js asks for the sign-in first, reads site.json beside the saved drafts' index (`meetOnLoad` in state/saved.svelte.js), and waits for the index before the stores are built only where it may let a part here go: a part this browser holds exactly as it last saw it saved, which is known before the index is read. Where there is none, the meeting goes on beside the load and lets go of nothing, and a publish, a discard and the first notice of new saves wait for it (`loadMeeting`). The page, the plugins, the collections, the templates and the redirects are then read together, each collection's and template's file beside the others, and the kept undo history is taken up once every store is built. The Legal panel reads the other pages and the front page's beacon once the canvas has answered its first handshake (`canvasOpened` in state/preview.svelte.js), so the canvas's own files go first. In the preview, the editing layer, its stylesheet and the admin dictionary are asked for as `boot()` starts, beside the site and the page.
- **Parts loaded on demand:** the windows and the panels opened now and then (`lib/parts.svelte.js`: the Nav, Site, Legal, Theme, Footer, Collections, Plugins, History, Updates and settings panels, the live phone, the CSV import, a page's settings, the collections table, the design picker, the link editor, the Urd settings, the shortcut sheet, the redirects, the picture editor, the setup wizard and the Drafts window) are each a file of its own beside editor.js, which holds everything the admin starts with (`codeSplitting` in vite.config.js, the `$initial` group joining the entry). Only a value that differs from its part's default is stored; where a part's default changes, `earlierDefaultWrites` reads its earlier default once per browser (run at the top of `menu/state.svelte.js`, marked by `urd-earlier-defaults-read`), so a design chosen before keeps its parts; the standing design and the parts that differ from it are read from the parts (`designState`) and never stored; choosing a design is the writes of `designWrites`, and `restoreWrites` of the values before it takes it back. The admin layouts' list (`ADMIN_LAYOUTS`) lives here and the shell imports it. `state/admin-design.svelte.js` puts them to work: the settings' context (`settingsContext`) carries the values, the standing design and `applyDesign`, which writes each part through its row's setter and then as stored, keeps the values before it for one undo while the parts stand as it left them, and names a changed part's design value on its row (`partNote`, `partBack`). The Urd settings window (`settings/SettingsBody.svelte`) draws `lib/settings-model.js`'s sections in its three groups (`SETTINGS_BANDS`: the admin designs, named Admin layout there with Presets first; Local settings; This site) open in one scroll, the design first as a pictured choice like the others (`lib/settings-pictures.js`, each design's one line its tile's tooltip) under `settings/AdminDesignRow.svelte`, the line naming the design that stands and what differs, with «Back to» and Undo.
- **The editor's own ids (ADR-0021):** the site themes' preset ids are English (well, stone, plum, ocean, night, with the `themePreset.*` keys in all five dictionaries) and are never persisted, since the active preset is derived from the stored tokens. The admin themes' ids (purple, well, gold, grey, aurora, dusk, ember) are persisted only in the browser's localStorage under `urd-admin-theme` and are migrated on read, as the draft keys are: the editor reads the old key when the new one is missing, writes the new key and deletes the old one, so no browser draft is lost. Custom CSS written by a site owner against old class names (`urd-handlekurv-*`, `urd-produkt-*` and the like) has to be updated to the English class names; the classes are runtime-generated and never persisted.
- **The preview's Screen device (ADR-0018):** its size (My window, a common size, a common aspect ratio at the width it stands at, or an own width with an optional height) is chosen in the Screen button's fold-out and kept per browser in localStorage under `urd-admin-screen`, read and written by `editor/src/lib/own-screen.js`; the Phone's under `urd-admin-phone` by `editor/src/lib/preview-width.js`, and the ratios by `editor/src/lib/aspect.js`. The binding limit of the content width (`contentWidth / (1 - 2 * gutter / 100)`) is the pure function `bindingWidth` in `editor/src/lib/content-width.js`, with its own test; the Site panel shows the width as four quick choices plus free adjustment from 960 to 1920, the side margin as a scale (None, Small, Medium, Large) with the raw vw number under Advanced, and a live sample against three real screen widths showing where the width binds.
- **The editor measures the canvas, never the section:** every geometry site in `preview-edit.js` (drag, resize, arrow keys, marquee, group drag, grid overlay, block menu, materialisation of mobile frames) takes its width from the shared `canvasOf` helper, so a forgotten measurement is mechanically searchable. `sticky.js` derives the block's left edge and width from the canvas rect and the release limit from the section's top and bottom, in separate variables; it reads the left edge with `parseFloat(el.style.left)`, so the inline `left` must stay a plain percentage (a `calc()` string yields NaN), which is one reason the content width is a canvas node and not a `calc()` in `frameToCss`.

**The state modules** (`editor/src/state/`, since 0.7.26.5). Each `.svelte.js` module holds its state as module-level `$state` and `$derived` with the functions that change it, and exports two things: a handle, `<name>State`, with a getter and a setter for every variable and its functions and constants as they are, and `effects()`, the module's `$effect` blocks, which the shell runs once at its start. Inside a module the names are bare; another module reaches them through the handle (`pageState.selectedBlock`), never through a copy, so every piece of state has one owner and a read follows it. The modules import each other freely; a read of another handle at load time would meet the import cycle, so loads read nothing across modules (tests/app-render.test.mjs loads them all).

- `shell`: the admin theme and language, the status toast, the sign-in (`auth`, `checkAuth`), the confirmation dialog, the setup wizard, `activePanel` and the panels preference, the top bar's fold steps (`FOLD_MQ`), the guides and the grid buttons, the keyboard, and `init`.
- `preview`: the iframe and the bridge to it (`onIframeLoad`, `onReady`), the device and the zoom, the Screen's and the Phone's sizes, the chrome, and the light or dark preview mode.
- `page`: the page draft (`store`), `pageId`, `selectPage`, `selectedBlock` and its mutators, the fits, the section mirrors and their mutators, the animations.
- `site`: `siteDraft` and `siteStore`, `siteMutate` and the nav, footer and theme mutators, the grid, the pages list with their slugs and search text, the icon, the calendars, the theme suggestions, the background contexts.
- `history`: one undo stack over every draft (`snapshot`, `pushHistory`, `undo`, `redo`, the `restore*` functions) and the dirty flag.
- `collections`, `templates`, `plugins`: their draft stores, views and mutators; `plugins` also the discovery, the live CSP and the plugin blocks.
- `updater`: the publish history and its revert, the update check and the update, the publish baseline.
- `publish`: the images materialised into media/ (lib/materialize.js, each in the folder of its kind), the commit of everything or of the parts ticked (lib/publish-pick.js), the deploy wait, the discard, and the tidy of media/ (lib/media-tidy.js).
- `drafts`: the Drafts window, opened from its tab in the System section: its place, pin and pill, its tab, the ticks (`urd-drafts-later`), this browser's name, autosave and Ctrl+S.

**The image editor** (0.7.29.2). One dialog (`lib/PictureEditor.svelte`, layout A: the picture large at its true shape with the crop window, which is dragged over it to choose what shows (the focus point the page draws it by, `movedFrame`), the shapes, the fit and the zoom under it, and Look, Turn, Adjust, Corners, Overlay, Text and Size in a column at the right) serves the image block, gallery pictures, collection and product pictures and the video's cover. The state (`state/picture-editor.svelte.js`) holds the picture as the dialog shows it (`readPicture` in `lib/picture-edit.js`) and writes every change at once through the place it lives (`mutateBlockAt` for a block, `mutateCollection` for an entry, `writePicture` for the fields) under one history key per opening, so the canvas shows it live and the whole edit is one undo step; the dialog keeps its own undo and redo while it is open, a slider's drag one of its steps, and Cancel or Escape writes the picture back as it was opened. An image block's frame goes with the picture there, so a shape (which keeps the frame's height and takes the width from the shape) is undone with it. A gallery picture's steps hold every picture's settings in the gallery beside it, so «Apply to all» (`withShared`: the look, the adjustments and the overlay) is undone and cancelled with the rest. ## The publishing flow (`template/functions/`)

Cloudflare Pages Functions - small serverless functions that ship with the repo and require zero operations ([ADR-0003](adr/0003-publishing-via-github-oauth-and-pages-functions.md)). The pattern is validated in production in ApeironLF.

| Endpoint | Role |
|---|---|
| `GET /api/github/login` | Starts the GitHub sign-in (state cookie against CSRF) |
| `GET /api/github/callback` | Exchanges the code for a token server-side; the token is stored in an httpOnly cookie and never reaches browser JS, and a token that expires keeps its refresh token beside it |
| `GET /api/github/me` | Login status + enforces `ALLOWED_LOGINS`; renews a sign-in that has fallen due |
| `POST /api/github/commit` | The core: commits all changed files as ONE commit via the Git Data API |
| `GET /api/github/latest` | HEAD + diff since the baseline SHA → conflict detection («Someone else has published») |
| `GET /api/github/history` | Latest commits → basis for undoing a publish |
| `POST /api/github/revert` | Forward revert of the last publish: a new commit on HEAD's tree that sets each file that publish changed back to how it stood before and leaves every other file as it stands (`_lib/revert-plan.js`), so an update made since is kept - history is never deleted |
| `POST /api/github/logout` | Signs out: expires the cookies and revokes the sign-in at GitHub, a renewable one renewed once and the new token revoked (best-effort, so the cookies go even when GitHub cannot be reached) |
| `GET/POST /api/github/drafts` | The saved drafts (ADR-0032) on their own branch, `urd-drafts`: the index, the parts' texts, and a save of several parts as one commit |

**The saved drafts' branch (ADR-0032):** `urd-drafts` holds `index.json` (`{ version: 1, parts: { <name>: { savedAt, saver, hash, base, title?, later?, note?, device? } } }`, with `savedAt` and `saver` written by the function, `note` the owner's words on the save (at most 200 characters) and `device` the name the owner gave the browser it was saved from (at most 40)) and one file per part, `parts/<name>.json` (`{ v: 1, keys: { <localStorage key>: <the stored draft text> } }`). A part is `site`, `collections`, `templates`, `plugins`, `redirects`, `page-<id>` or `collection-<id>`, and holds only its own stored keys (`keyOfPart` in `functions/_lib/drafts.js`). A save names the head it last read (`expect`), and one that moved answers 409 `draftsRace` with the head as it stands; the first save makes the branch (`commitTree` with `orphan`). Every commit message begins with `[CF-Pages-Skip]`, so the host builds nothing from the branch; the function never writes the site's branch, and refuses where the site's branch is `urd-drafts` itself. In the editor, the Drafts tab first in the System section opens the Drafts window (`shell/DraftsWindow.svelte` on `lib/FloatWindow.svelte`, its state in `state/drafts.svelte.js`): a window over the canvas placed by its tab (`placeByTab` in `lib/menu-place.js`) or where it was dragged, that place kept across a reload for the browser tab's session (`urd-drafts-place` in sessionStorage), pinned or folded to a pill per browser (`urd-drafts-pinned`, `urd-drafts-pill`), with the tabs This browser, Saved and Live; the unticked parts are kept in `urd-drafts-later`, the browser's name in `urd-browser-name` and autosave in `urd-drafts-autosave`; `state/saved.svelte.js` reads and writes the branch, keeping what this browser last saw of each saved part in `urd-saved-seen` and what the Saved tab last showed in `urd-saved-noticed`. A saved page's row lists what changed against this browser's version (`lib/page-diff.js`, by the ids of sections and blocks). «Look» draws a saved page or the saved site settings in the canvas (`startLook` in `state/preview.svelte.js`, the banner `shell/LookBanner.svelte`): the bridge holds the draft's own sends and drops the page's edits while it stands (`setLooking` in `lib/previewBridge.js`), the canvas's handles are off and the panel column inert, and «Back to mine» sends the draft again. «New tab» opens the tab within the press and hands the saved texts over under a one-time key `urd-look-<id>` (`{at, texts}`, kept a minute for a tab that never loads), which the draft view (`?draft=look&look=<id>`) moves into its own session storage and draws over this browser's drafts (`receiveLook` and `overlayDrafts` in the engine's `drafts.js`). «Keep both» adds the saved version as a page of its own through `duplicatePage`, one undo step that takes the copy's draft with it.

**Choosing what to publish (ADR-0032 decision 2):** the ticks the Drafts window keeps in `urd-drafts-later` stand on the rows of the Publish menu and History's «Not published yet» too (`lib/UnpublishedRows.svelte`), and Publish, the palette and the Drafts window's «Publish ticked» send what is ticked (`publishTicked` in `state/publish.svelte.js`). `lib/publish-pick.js` decides what goes: `pickParts` takes the parts waiting and the unticked ones and follows the ties (a page not live yet takes the site settings, a collection not live yet the collections' list, the site settings and the redirects go together, and the media tidy's moves waiting take everything), returning the parts going, why an unticked part goes anyway (shown ticked and fixed in the rows, with the part it goes with) and the parts kept; `outSite` builds the site file that goes out with each page not live yet that stays behind marked hidden, and the collections' list goes out without a new collection that stays behind. `publish({ parts })` gathers only the parts going and, after the commit, adopts only their stores as published; the site store's baseline is the file as it went out, its draft kept as it stands. A page whose entry went out hidden before its file is kept in the admin key `urd-not-live` (`lib/not-live.js`) until its file goes: the site settings count as waiting only for differences beyond that hidden flag (`siteWaits` in `state/history.svelte.js`), and publishing such a page takes the site settings with it. A partial publish marks its time per part in `urd-published-at-parts` (`markPublished` and `publishedAtOf` in `state/history.svelte.js`), so a kept part's row still lists its steps, and the kept parts that stand in this browser alone are saved to the drafts branch quietly.

Security layers (defence in depth):

1. **No admin password** - *editing* locally is harmless; the gate is that only GitHub-logged-in users in `ALLOWED_LOGINS` can *commit*.
2. **Path allowlist in `guard.js`:** publishing can only write `content/**` (json, css, and xml only as a feed that can run nothing: an `rss`, `feed` or `urlset` root, no DOCTYPE, entity or stylesheet instruction, and no XHTML, SVG or MathML namespace, `isAllowedXml`, which holds `sitemap.xml` too), `media/**` (image, audio and video extensions, and `pdf` only when the content starts as a PDF and stays within 15 MB, `isAllowedContent`; a move within `media/` keeps the extension, `isAllowedMove`, and takes the blob the repository holds, never a sha from the client), `plugins/plugins.json`, the visibility files `sitemap.xml` and `robots.txt`, the host's redirect file `_redirects` (only in the shape publishing writes it from `content/redirects.json`: comment lines, and an old address, a path or http(s) target and 301 or 302 a line, none from Urd's own addresses, `isAllowedRedirects`; ADR-0015), and per-page routing copies (`<slug>/index.html`, never reserved folders, each written as the blob the repository's own `index.html` holds, never from what the request sends: `copyOf` in `commitFiles`), and delete a plugin's whole folder (`plugins/<id>`, `isDeletablePath`; a deletion of a folder removes every file under it, and nothing is ever written there) - never `functions/**`, `.github/**`, `admin/**`, `assets/engine/**`, `assets/urd/**`, `_headers`, `urd.json`, the root `index.html`, `404.html`, `.gitignore` or `wrangler.toml`. A hijacked editor session therefore cannot plant code. The `commit` endpoint takes `{message, files:[{path,content,encoding}]}` and creates one commit through the Git Data API: blobs, then a tree, then a commit, then the ref is moved; `latest?base=<sha>` returns whether other people have published since the editor loaded (the base SHA the draft was built on).
3. **Conflict guard in two layers:** the editor compares against the baseline SHA (`latest?base=`) and warns on overlapping files; the commit endpoint additionally rejects with 409 if HEAD has moved since the check (optional `expect` in the request). Without `expect` (older clients, direct API use) the server-side guard does not exist.
4. **Calls from the site's own pages, as JSON:** `requirePublisher` (`_lib/auth.js`) refuses a call from another site (Sec-Fetch-Site, with Origin as the fallback), and a call that changes something unless it is sent as JSON (415 `notJson`), which a form cannot send, not even one planted on the site's own pages; the checkout endpoints refuse an order that is not JSON the same way. The open routes answer the site's own pages only (`fromOwnPages` in `_lib/photos.js`: `/api/photos` and `/api/photo` for a photo source's pictures, `/api/ics` for the calendar), so a client that sends neither fetch metadata nor an Origin or Referer, such as an image search's crawler, is refused and a photo source's pictures stay out of image search; `/api/geocode` answers a signed-in publisher only, its answer kept by that browser alone (`private`). `functions/api/_middleware.js` gives every function's answer `nosniff`, and one that is not a web page a policy that runs nothing (`default-src 'none'; sandbox`), since `_headers` reaches the static files only.

Configuration is environment variables at the host: `GITHUB_REPO`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` and `ALLOWED_LOGINS`, with `GITHUB_BRANCH` (`main`), `GITHUB_SCOPE` (`public_repo`, an OAuth App's only) and `GITHUB_ROOT_DIR` where they differ (`cfg` in `_lib/github.js`).

**The sign-in (ADR-0003):** a GitHub App per site, installed on the site's repository alone with Contents read and write; an OAuth App goes through the same flow. The login asks for `offline_access` beside `GITHUB_SCOPE` (`loginScope`), so an OAuth App's sign-in lasts eight hours whatever the app's setting for expiring tokens, as a GitHub App's does with «Expire user authorization tokens» (on by default), and GitHub's answer carries a refresh token for six months. `_lib/session.js` keeps the sign-in in `urd_gh` (Path `/`) and the end and the refresh token in `urd_ghr` (`<seconds>.<token>`, Path `/api/github`, so the site's functions get it and its pages never do), both httpOnly. A renewal ends the old sign-in and the old refresh token at GitHub, so only `me.js` renews: once the sign-in is within `RENEW_BEFORE` (15 minutes) of its end, or its cookie is gone, it renews, sets both cookies and answers `renewIn`, the seconds until the editor asks again. The editor (`checkAuth` in state/shell.svelte.js) plans that ask, keeps its time in `urd-sign-in-renew`, and asks before any other call to GitHub where it opens with the renewal due and as the tab comes back into view; before a publish or a save of drafts it asks with `?soon=1` where the renewal is within five minutes (`renewIfDue`, `RENEW_SOON`), so the planned renewal does not end the sign-in under them. The status call goes one at a time, shared within a tab and held by the Web Lock `urd-sign-in` across tabs where the browser has one, so a later tab asks with the cookies the earlier one was given; without an answer, or with the host or GitHub down, the sign-in shown is kept and a renewal due asked for again in a minute. A refused renewal (`renewFailed`, as when another tab renewed a moment before with the same refresh token) expires no cookie, the editor asks once more 1.5 s later, and a tab left showing the sign-in as ended asks again as another tab plans a new renewal (the `storage` event). Signing out renews a renewable sign-in once and revokes the new token, which ends the old token and the old refresh token, and expires both cookies.

### The payment layer (ADR-0020, ADR-0028)

The checkout function creates the payment on the Vipps MobilePay ePayment API (a wallet payment by web redirect, the reference as the idempotency key) with `returnUrl` set to the checkout page with `?ordered=<reference>`, the order lines and the typed contact fields in the description, the lines as the receipt in the buyer's app for a seller outside the VAT register, and the profile scope that asks the app for the name, the email and the phone; the money is reserved, and the seller captures it in the Vipps portal when the goods ship. On the return the checkout block asks `/api/pay/vipps/session`, which reads the payment's state and the shared contact details from Vipps, and shows a receipt by name and empties the cart for a reserved payment only. The webhook endpoint `/api/pay/vipps/webhook` takes the payment events of a registration the owner makes, checks the HMAC-SHA256 signature against the registration's secret, and stores nothing: the orders live in the Vipps portal, and the site has no order database. `functions/_lib/order.js` owns the order logic every provider shares (payload validation, the total in the currency's minor unit, the variants, the line items and the description, the reference, the site's currency and the shop files) and `functions/_lib/vipps.js` the Vipps part (the payment body for the app or the card page, the receipt lines, the reading of a payment's state, the token cache, the webhook signature), both tested in node; `functions/_lib/vipps-api.js` owns the network side (the access token kept in the isolate, one call shape with the common headers and a timeout); `functions/api/pay/vipps/checkout.js`, `session.js` and `webhook.js` are thin shells around them, and every other provider of [ADR-0028](adr/0028-payment-providers-in-the-optional-layer.md) follows the same three files under `/api/pay/<provider>/`; each checkout endpoint also answers a GET with whether its provider is set up, which the editor's checkout block asks on a click so the owner sees a missing key while building. Stripe (`functions/_lib/stripe.js` and `stripe-api.js`, with the timed fetch shared in `net.js`) creates a Checkout Session on Stripe's hosted page with the lines as price data and a hold unless the block captures at the order, answers the page with the session's id beside the reference, and its session endpoint confirms a session only when its `client_reference_id` is that reference and its PaymentIntent is held or captured; the webhook checks the Stripe-Signature HMAC within five minutes. PayPal (`functions/_lib/paypal.js` and `paypal-api.js`, with the OAuth token kept in the isolate) creates an order with intent CAPTURE and PayPal's own approval page; its session endpoint, a POST only, reads the order, refuses one made for another reference, and captures an approved order with the reference as PayPal's request id, so a repeated ask captures nothing twice; the webhook asks PayPal's verify-webhook-signature with the event sent back exactly as it arrived. Every checkout endpoint runs `prepareOrder` (order.js) first: the payload, the published catalogue, the variants with the size and colour a product asks for, the basket's prices (a price that is not the catalogue's answers 409 `orderPrices` with the prices that hold, which the basket takes, `cartReprice` in shop.js), and the checkout block on the published page the order returns to offering this provider in this way (`pageCheckout`, `offersPayment`; none gives 400 `payNotOffered`, with no other block's settings borrowed). The checkout hands the page a buyer key, an HMAC of the reference with the provider's secret (`buyerKey`), so nothing is stored for it. The page keeps the provider, the reference, the provider's id and the key in sessionStorage when it sends the buyer away, so the return never takes the provider's id from the address, and asks every provider's session endpoint with a POST carrying the key (`x-urd-key`); the answer names the buyer and the amount the provider confirms only with the key (`sessionAnswer`), so a shared return address tells whether a payment went through and nothing more, and the confirmation's total is that amount. The secrets they need are listed in [DEVELOPMENT-en-GB.md](languages/DEVELOPMENT-en-GB.md#common-tasks).

In early development the schema, engine and editor change in the same commit, and the built editor in `template/admin/assets/` must always match the engine from the same commit - hence one repo for now ([ADR-0004](adr/0004-monorepo-with-template-folder.md)). At every release the release Action (`.github/workflows/release.yml`) syncs the contents of `template/` to the clean `urd-template` repo («Use this template») as one squashed commit, tagged with the version.

## Engine versioning (ADR-0013)

The engine lives in a versioned folder, `template/assets/engine/<version>/`, where the folder name is always equal to the `engine` field in urd.json (test-enforced). This makes the whole import graph addressable per version (relative ES imports inherit no `?v=` query), so the template's `_headers` can give `/assets/engine/*` immutable caching with a version-neutral rule that never needs changing. The monorepo's `template/_headers` revalidates the engine instead (`no-cache`), since its files change between releases under the same folder, and the release sync writes the template's rule (`scripts/release-headers.mjs`, ADR-0013 decision 2). The stable plugin API lives in `template/assets/urd/`: shell modules (i18n, hint, dropdown and others) that re-export from the current version and are revalidated normally - plugins never hard-code the versioned path. Any mechanism that switches the engine version (phase releases, the updater) writes the root index.html and all `<slug>/index.html` copies in the same commit (the copy-refresh duty).

The dynamic imports in the engine's `i18n.js` and `plugins.js` (admin dictionaries, language packs) go through the `/assets/urd/` shells, not relative paths, because the same lines run from the editor bundle, where a relative path would resolve against the bundle's location.

## The update mechanism (ADR-0014)

`template/urd.json` is the manifest: engine version + the ownership map (`ownedPaths` for Urd-owned paths, `userPaths` for `content/**`, `media/**`, `plugins/**`). The Updates panel in admin checks against the `urd-template` repo via `/api/github/update`: the user's git tree is compared with the template's tree at the BASELINE (the tag `v<engine>` for the version the site is running) and at the target version, using pure blob-SHA comparisons - an equal SHA is identical content, so «hand-edited» is decided without loading a single file. Execution writes the Urd-owned files as ONE atomic commit (inline trees, expect guard): the engine atom group is always switched as a whole, optional files (functions, loose root files) can be held back per file, `_headers` is never written (a diff instruction instead, cf. ADR-0006), and user-owned paths are never touched. An update only goes forward: a target older than the installed version is refused (`updateOlder`, `isOlderTag` in update-plan.js). Content written on an old schema is lifted by the migration contract at load time; that is the whole point of it.

The updater is `functions/api/github/update.js`: GET runs the check, POST performs the update, and both open with the same `requirePublisher` prologue as publishing. The check carries the template repo's release of the version on offer, or of the one installed where the site is up to date: its name and its page on github.com, which the Update panel shows with the version as a link (`releaseLabel`), and the notes of the one on offer, their first 20 000 characters, which the panel reads as Markdown (`lib/release-notes.js`: headings, lists, code, links to http and https only, and GitHub's `<details>` folds) and draws with its own elements, never as HTML (`lib/ReleaseNotes.svelte`). `guard.js` holds the ownership map `OWNED_PATTERNS` / `USER_PATTERNS`, mirroring `ownedPaths` / `userPaths` in urd.json and contract-tested against it, with the predicates `isOwnedPath` / `isUserPath`; a completeness test requires that every actual file in the template matches exactly one ownership class. The perform step fetches all target texts in ONE GraphQL call (`Blob.text` via aliases), builds the Git tree with inline `content` (never one blob POST per file), chunked into chained `base_tree` trees for large volumes, and commits with `expect` protection (409 when HEAD has moved). Binary and truncated blobs take the REST detour (base64 from the template repo straight in as a blob in the user's repo, two subrequests each), at most `BLOB_BATCH` (18) per call: ONE GraphQL call first tells which target files are such blobs and which of them the user's repo already holds (`object(oid:)` on the user's repo; pure `blobBatch` in update-plan.js picks the next batch), a call that copies a batch answers 429 `updateContinue` with `copied` and `total`, and the Updates panel repeats the call while it copies more, until a call that finds at most `BLOB_ROOM` (10) left copies those and commits with the tree referring to them by the template's SHAs, so an update with few such files is one call as before. The subrequest budget is about 8 for the check, about 43 for a copying call and at most about 33 for the committing one, under the cap of 50 on the free plan; a call that goes over keeps what it copied, and the next one goes on from there. The error codes are `api.update*` keys in all five admin dictionaries, enforced by the i18n contract test.

## Inheritance from ApeironLF - what is fixed by design

| Weakness in ApeironLF | The Urd solution |
|---|---|
| Ad-hoc `normalize()` without formal versioning | `version` + stepwise `migrations` on all types; `schemaVersion` at file level |

# Architecture

This document describes how Urd fits together. The data model - the contract everything builds on - is in [SCHEMA.md](SCHEMA.md). The reasoning behind the design choices is in [adr/](adr/).

## System overview

```
VISITOR                            EDITOR
   │                                  │
   ▼                                  ▼
yoursite.no ─────────────────► yoursite.no/admin
   │                                  │ GitHub login (OAuth)
   │  static files:                   ▼
   │  index.html                prebuilt editor (Svelte, compiled)
   │  assets/engine/*  ◄──┐           │
   │  content/**.json     │           │ draft in localStorage
   │  media/*             │           ▼
   │                      └── iframe preview: the REAL site,
   ▼                          draft pushed via postMessage
 the engine renders the site          │
 from content/ data                   │ «Publish»
                                      ▼
                          functions/api/github/* (Pages Functions)
                                      │ one commit via Git Data API
                                      ▼
                                GitHub repo  ──►  the host deploys (~1 min)
```

Two worlds, one repo:

- **The visitor site** is raw static files: `index.html` loads the hand-written engine (`assets/engine/`), which reads `content/site.json` + `content/pages/*.json` and builds the DOM. No build process, no framework.
- **Admin** (`admin/`) is a prebuilt Svelte app that is committed as static files. It edits the same JSON files, previews them through the real site in an iframe, and publishes via serverless functions.

## The engine (`template/assets/engine/`)

Hand-written, readable, dependency-free ES module JavaScript - never compiled ([ADR-0002](adr/0002-svelte-for-editor-readable-js-for-engine.md)). The ownership promise applies to what the visitor loads, and the editor's preview iframe loads exactly these files - preview fidelity is therefore structural, not something that has to be maintained.

Core parts:

- **`urd.js`** - entry point. Creates `window.Urd` with the registries, loads site + page, runs migration and render.
- **`registry.js`** - shared registry factory. All extensible types use the same pattern:
  ```js
  Urd.blocks.define('text', { version, label, defaults, migrations, render, mount? });
  Urd.sections.definePreset('hero', { label, create });
  Urd.backgrounds.define('gradient', { version, label, defaults, migrations, render });
  Urd.animations.define('fade-in', { version, label, defaults, migrations, apply });
  ```
  Plugins use the identical APIs - the core and plugins are equals.
- **`migrate.js`** - stepwise version lifting at load time. The most important file in Urd; see [ADR-0005](adr/0005-versioning-and-migration.md). Lifting happens in memory - the files on disk are only written at the next publish. Unknown type → neutral placeholder, data kept untouched. The load rule is `while (data.version < def.version) props = def.migrations[data.version++](props)`; the machinery (`lift`, `liftPageFile`, `liftSiteFile`) and the empty `migrations: {}` contracts of the core types are covered by the synthetic tests in `tests/migrate.test.mjs` and are the foundation the updater (ADR-0014) builds on. Until the first real format change after v1.0, schema validation (`npm run validate` + CI) is the active protection for the contract. The page migrations are listed in [SCHEMA.md](SCHEMA.md#the-page-migrations).
- **`render.js`** - render loop: page → sections → background layers + blocks. Translates grid units (columns/rows) into CSS. Incremental: a single changed section is re-rendered on its own (used by the preview). On mobile the blocks go into a row grid inside `.urd-canvas` (ADR-0019): `grid-template-columns: 100%` and `grid-auto-rows: minmax(8px, auto)`, with `MOBILE_ROW = 8` exported from `migrate.js`. Flow blocks are auto-placed (sparse) in `stackOrder` order; a block that is neither text nor auto-growing spans `ceil((desktop.h + 16) / 8)` rows (the 16 accommodates the flow spacing, so the row tracks are never inflated), while text and auto-growing blocks span one row and take their natural height. Pinned blocks get `grid-row: row / span rows`, `width: w%` and `margin-left: x%` of the surface, plus `z` and `rot`. `stackOrder` and `mobilePlacementToCss` are pure functions.
- **`theme.js`** - maps `theme.tokens` from `site.json` to CSS variables (`--urd-color-bg`, `--urd-font-heading`, …). When the theme has no `accent-text` token, `buildThemeCss` writes the effective value (the background colour) as the fallback in `:root` and, behind `@supports (color: contrast-color(#000))`, lets the browser pick black or white against the accent with `contrast-color()`; an owner-set token is written as it is, and «Auto» in the Theme panel removes it.
- **`sanitize.js`** - the shared sanitiser: strips event attributes, `script`/`iframe`/`object`/`embed` elements and `javascript:` links at render. The text blocks and the collection entries' `title` and `text` go through the same function.
- **`hint.js`** - the help chip of ADR-0008: `attachHint(host, { title, lines })` attaches the «?» chip to a block or section host and owns the help card; the chip and the card are styled in base.css. Plugins import the same helper from the stable path `/assets/urd/hint.js` (ADR-0013) and call it only when `ctx.preview` is true.
- **`i18n.js`** - the two dictionaries of ADR-0012. The admin language is stored in localStorage under `urd-admin-lang`, shared by the admin and the preview iframe (same origin). `locales/site/nb.js` is imported statically (preloaded); other site languages are dynamically imported in `boot()` after site.json is read, on top of a FRESH copy of the base, and that import is deliberately invisible to the modulepreload contract. `boot()` sets `document.documentElement.lang` (the shells hardcode `no` only as the pre-JS default). The editor's main.js imports the admin dictionary from the engine's `locales/admin/<lang>.js` at runtime before mount, and the preview's canvas chrome does the same lookup itself; a language switch is a reload because of the roughly 900 `ta()` call sites. The language-pack lookup lives in `language-packs.js`, deliberately OUTSIDE the engine's static import closure: it is fetched only when a language the core does not have is asked for.
- **`mcp/`** (the optional MCP server, ADR-0017) finds the site root with `new URL('..', import.meta.url)`, which resolves to `template/` in the monorepo and to the clone root in a cloned site, reads `urd.json.engine` and imports the engine from the versioned folder, the same way `tests/_engine.mjs` and `editor/scripts/validate.mjs` do. `RESERVED_SLUGS` is exported from `guard.js` and imported by the server; the editor keeps the second copy named in AGENTS.md, and there is no third.
- **`nav.js`** - builds the navigation from the page registry in `site.json`. Nothing is hard-coded: nav, routing and admin panel lists are all derived from the same registry.

### The navigation bar's sizing (ADR-0023)

The size preset `nav.style.size` (sm/md/lg/xl) is a `urd-nav-size-*` class on the nav that sets `--urd-nav-size-pad` and a font size in rem. Free values override it through inline custom properties on the nav element: `nav.style.padY` as `--urd-nav-pad-y` and `nav.style.textSize` as an inline `font-size`. The chain in `base.css` is `--urd-nav-base-pad: var(--urd-nav-pad-y, var(--urd-nav-size-pad, 0.9rem))`, so a stored padY wins over the preset and the preset over the fallback. The floating pill multiplies the preset padding by 0.67 by overriding `--urd-nav-base-pad`, never the derived `--urd-nav-pad`, so an explicit padY stays raw in every variant. With an image logo the bar's height has a floor of 36 px whatever padY says, because the logo's margin calibration contributes a constant.

The side padding is `--urd-nav-px`, which defaults to the fluid `clamp(1rem, 4vw, 2.5rem)` and is set directly by `nav.style.padX`; the mobile panel and the side-to-bar fallback read the same variable. With `nav.style.inset` the side padding on desktop becomes `max(padX, the desktop gutter, (100% - canvas width) / 2)`, resolved against the body-wide host, the same reference the canvas uses (`--urd-canvas-w` and `--urd-canvas-gutter-desktop`, set on `<html>` by `applySiteLayout`). The floating pill is `min(1100px, 100% - 2rem)` by default; `nav.style.pillWidth` replaces the 1100 px with a px value or, for the string `content`, with the content width less the desktop gutters, and the override is suppressed at the mobile breakpoint, where the pill keeps `100% - 2rem`.

The mobile and compact overrides are chosen by the pure helper `navSizeVars(style, logo, { mobile })` in `nav-model.js` and written inline by `nav.js` at render time. The compact factor `nav.style.shrinkTo` lives inline on the nav element as `--urd-nav-shrink-to` while the host carries the state class, and the compact rule targets the nav: `.urd-nav-compact .urd-nav { --urd-nav-shrink: var(--urd-nav-shrink-to, 0.5) }` (the default factor is 0.5). The logo height is written as `--urd-logo-base` on the img, and the CSS derives the rendered size from it so the shrink-logo rule can scale it with the padding. Border and shadow are allowlisted classes: `urd-nav-border-<side>` with the width and colour as custom properties, and `urd-nav-shadow-<strength>` (soft/strong). The side column keeps its own padding, `1.2rem 1rem`; `padY` and `padX` do not touch it. The editor's `setNavStyle` deletes a key when it is set to undefined, and an emptied `mobile` object is removed, so defaults are never written to the file.

### Desktop sizing: the push pass, the fit and the gestures

The decisions are in [ADR-0024](adr/0024-content-push-on-the-desktop-canvas.md) (content push) and [ADR-0025](adr/0025-the-sizing-model.md) (the sizing model); this is how they are built. The pure parts are in `push-model.js` (`pushLayout`, `fitMoves`, `followsContent`, `heightAlign`, the type sets) and tested in node; the measuring parts are in `render.js` and `preview-edit.js`.

- **The push pass** (`applyPush` in render.js) runs for every desktop section one animation frame after the blocks' own measurements, and again on every `ResizeObserver` notification from a block or its content (fonts, images, feeds, width changes), deduplicated to one pass per frame per section. For each block it writes the frame's height, applies the shrink (`fitContent`), measures the height the content needs as `max(offsetHeight, scrollHeight)` of the content children with the box at the design height (so overflowing text counts; the editing handles never count, and a zoomed child is converted to the block's px), and asks `pushLayout` for the shifts with the gap thresholds `PUSH_GAP_MAX` (70 px) and `PUSH_GAP_MIN` (10 px); `frameToCss` writes the design position from `frames.desktop`, the pass writes the shifts as `style.top` and `data-urd-shift`, the drawn height as `data-urd-drawn`, and a pass without growth writes the design positions back. The measurement is two-way: the box grows with its content and returns to the design height when the content fits again. A block pinned by sticky.js keeps its stash up to date instead of its inline top, so a release lands right. The shrink of `fit: "shrink"` is a bisection between full size and `fitMin`, run before the box height is measured, so the content is zoomed only as much as the design height needs; for image, video, shape and icon the same fields are a floor on the frame's width (`fitFloorPx`): the frame follows the canvas in percent but never gets narrower than the floor times its design width, capped at the canvas's right edge. A block that follows its content (`data-urd-height="content"`) is measured by `hugHeight`: its natural height when it is drawn at its content, or 0 to keep the frame while it is still loading (`aria-busy`). Such a block is observed through its content children alone, since a box the observer watches and the pass resizes in its own callback would come back as a notification it cannot deliver in the same frame.
- **Editor-only parts never push.** The image adders, the «+ Product» card, the placeholders of empty fields and the calendar's notes about removed lines are drawn in the preview but are not on the page; `EDITOR_ONLY` in render.js lists them, base.css hides the same list under `.urd-fit-measure`, and a test holds the two equal. The pass draws a block with them but measures its growth as a visitor sees it (`asVisitor`, `visitorHeights`), so the editor's section heights are the published page's.
- **The section line.** `writePush` sets the section's inline min-height from `data-urd-min-height` (the section's own height, or the blocks' extent when it has none, kept there so the section returns to it when the growth is gone) and counts a block towards the section only while its design bottom is inside that height. In the preview (`_urdPushPreview`, set by `wirePush`) a section with a height of its own is never raised by growth; on the published page it is raised to the pushed bottom plus `PUSH_SECTION_PAD` (24 px). A section without a height of its own follows every block in both.
- **Snapping (snap-model.js, 0.7.10).** A dragged block snaps to the edges and centres of its neighbours, to the content surface's quarters and midline, and to the gaps its neighbours keep between them (equal-gap snapping, the tldraw rule), within eight screen px whatever the preview's zoom (`snapTolerance` from `--urd-chrome-scale`, the Excalidraw rule). The targets come from the section the block came from and the section its centre is held over, measured in the source canvas's px, and the lines are drawn there: a line between the block and a neighbour spans the two, a line of the content surface spans its section, and an equal gap is a band with its size. The grid overlay stands on every section while a block is moved, since a block released with its whole box outside its own section moves to the section under its centre; a block that still overlaps its own section stays and lies over the neighbour (ADR-0025 decision 8). Ctrl or Cmd turns the grid and the guides off for the drag; Shift holds a move to one axis, and on a resize of a block whose size is its frame it keeps the ratio.
- **The pass stands still under a gesture.** `suspendPush`/`resumePush` sit beside `suspendSticky`/`resumeSticky` in preview-edit.js. While suspended the pass touches nothing; the drag draws its block at the frame plus the block's own shift (`pushShiftOf`, read from `data-urd-shift`) while the frame it writes stays free of the shift, and the pass runs again from the new frames on release. Smart guides and the marquee measure `offsetTop`, which is the shown position, and the guide comparison adds the dragged block's shift so it aligns what the owner sees.
- **The row grid that was not taken.** A desktop row grid (the alternative ADR-0024 rejected) would rewrite about twenty files (`frameToCss` and the desktop branch of render.js, base.css, sticky.js, twelve sites in preview-edit.js, place.js, section-size.js, selection.js, section-layouts.js, the 112 hand-written frames in sections/presets.js, templates-model.js, preset-thumb.js, migrate.js) and ten test files, and break several invariants: sticky.js reads a block's `y` from `style.top` and writes it back when parked, `.urd-canvas` must leave `position: absolute` (ADR-0018), `y` may be negative for blocks hanging above the section, sections never clip while a grid reserves space for every item, 100 of the 112 preset `y` and `h` values are not aligned to a row step, `mobileOrder` and the presets' card order use desktop `y` as a pixel-scale key, and a row step would have to be a model constant rather than `grid.size`.
- **The fit.** After an edit of a block that follows its content, the editor (`fitBlockSoon` in App.svelte, debounced per block with a sequence number so only the latest answer counts) posts `urd-fit-block`; the preview measures the block at rest as a visitor sees it, three times to catch a design drawn by a module loaded on demand or a feed answering late, and answers with `urd-grow` carrying `fit: true`. The editor writes the height into `frames.desktop.h`, moves the blocks below by `fitMoves` (the push rules applied to the growth, so the data takes over what the pass drew) and sends `urd-frames`; the preview puts the frames into the section the pass holds (`updateFrames`) without drawing it again, so a caret in the block's text survives a fit that follows typing. The measure leaves out the unfolded part of open `<details>` (`unfoldedHeight`): an FAQ answer or a calendar fold a visitor opened is view state.
- **The gestures.** At the first move of a drag, a resize, an arrow key, align or distribute, `settleFrames` in preview-edit.js settles the frames of the blocks under the gesture to the boxes the pass draws for them (a block that follows its content takes its resting height, any other block its growth) and moves the blocks below by `fitMovesAll`, writing into the section the pass and the editing layer hold; the settled frames go to the editor as `urd-move` messages in the gesture's undo step (`postSettled`), and a gesture that changes nothing calls the settle's `undo`. While a gesture runs the pass is suspended (`suspendPush`/`resumePush`) and `pushPreview` draws the push as it will be on release from the frames under the pointer; the blocks being moved are left out of the section height, a resize keeps its block in it. The lower handle of a block that follows its content changes the width only, and a pull up or down shows the stop bar (`.urd-edit-stop`) at the content's edge; a fit that lands during the drag (`urd-frames` into the same block) wins over the height the drag began with. A block given its own height (`height.mode: "own"`) is no longer `followsContent`, so every path above treats it as a box.
- **The content in a box with its own height.** `heightAlign` reads the block's `height.align`, render.js writes it as `data-urd-align` on the block in both the desktop and the mobile branch, and base.css lays such a block out as a grid of one row: the content keeps its own height and moves to the middle or the bottom, or takes the row with stretch, which each type's own layout then fills (the figure centred, the countdown's units grown, a quote's card filled, the plain list and card calendar views spreading their rows and cards under the finding tools and over the subscribe row, with the calendar root as a flex column for that case). The editing handles and badges are absolutely placed and stay out of the row.
- **The block's own width.** The blocks with columns, cards or a layout that changes when the box is narrow (`FOLLOWS_WIDTH`) are marked `data-urd-width="own"` and are size containers named `urd-block` in base.css; other blocks are not, since a container box would hold a fixed-position descendant, which a plugin block may have. A rule that asks the block's width is a container query, and the window's media query it replaces stays beside it behind `@supports not (container-type: inline-size)` with the same declarations; a test holds the two equal. The calendar's narrow layouts are a different DOM (dots that open the day, stacked days) and are chosen in script by the block's width, read from a zero-height ruler beside the calendar so the pass's changes to the block's height never reach the observer. Galleries and product cards write a wide and a narrow column count and let the container query pick.
- **The map.** The map's box is its frame: `.urd-map` is a grid of the iframe row and the «Larger map» line, and the iframe fills what the frame leaves. The height setting it had until page schemaVersion 4 is lifted into the frame by `liftMapHeights` in migrate.js (the page migration 4 → 5, and template insertion), which gives the frame the height the map showed and moves the blocks below as a fit would.

## The editor (`editor/` → `template/admin/assets/`)

Written in Svelte 5 + Vite in the main Urd repo. At release it is built to static files in `template/admin/assets/` which are **committed** - associations that clone the template get a ready-made editor and never touch npm. The source code is open here; the compiled files in cloned repos are its product.

Key mechanisms (patterns validated in ApeironLF):

- **Draft:** all editing is written continuously to `localStorage`. A «baseline» (the published state) is compared against the draft; if they are equal, the draft is removed - this keeps the «unpublished changes» marker always honest.
- **Preview:** the editor shows the real site in an iframe with `?preview=1` and pushes the draft via `postMessage`. The engine listens and re-renders incrementally.
- **Panels:** the rail lists the panels (pages, nav, site, theme, blocks, grid, properties, footer, collections, plugins, history, update), and the one shown is `activePanel`; the Properties panel follows the selection in the preview. There is no panel registry, and plugins provide blocks and language packs, never panels.
- **Mobile review:** the editor enforces the flag rules in [SCHEMA.md](SCHEMA.md#mobile-review) - if you change the desktop layout in a section with a manual mobile layout, the section is flagged until you have looked over the mobile view. The mobile messages between editor and engine are `urd-mobile-reset {sectionId, blockId?}` (per block when `blockId` is given, per section otherwise); sections have no mobile mode, so there is no manual/auto message. In mobile view Delete and Backspace are guarded in `preview-edit.js` and the delete button is hidden, so deletion happens only on desktop; the per-section reset asks for a second click before it runs.
- **Collections:** edited in the Collections panel with a draftStore per collection; images are materialised at publish, and the preview renders from the draft via the bridge, which posts a `$state.snapshot` of it (a `$state` proxy gives DataCloneError).
- **Themed components (ADR-0009):** admin uses `<Dropdown value={…} options={[[value, label], …]} onchange={(v) => …} />` (Dropdown.svelte). The canvas and plugins use `createDropdown({ value, options, onchange, title })` from the engine's `dropdown.js` (`/assets/urd/dropdown.js` for plugins); it does not steal focus (mousedown prevented), so a text selection survives the choice. Segment buttons cover small option sets of two to five short labels.
- **Floating menus and anchoring (ADR-0011):** CSS Anchor Positioning is baseline in Chrome 125, Safari 18.2 and Firefox 147 for the core, with `position-try-fallbacks` from Safari 26 and Firefox 147; `contrast-color()` is Baseline Newly available since April 2026 (Chrome 147, Firefox 146, Safari 26). The editor's floating menus (`Dropdown.svelte`, `ColorPicker.svelte`, `GlyphPicker.svelte`, the engine's `dropdown.js` and `color-picker.js`) open in the top layer with the Popover API, are placed against their button by `position-anchor` and `position-area`, and are flipped away from the viewport edge by `position-try-fallbacks`; light dismiss owns the outside click and Escape. `anchored.js` requires the Popover API, `anchor-name` AND `position-try-fallbacks` before the modern branch is taken, so a browser with anchors but no fallbacks (Safari 18.2 to 25) stays on the JS branch; the CSS nests the two `@supports` blocks so the declarations are inert where unsupported. The measuring JS branch (`position: fixed`, `getBoundingClientRect`, flip and clamp, document listeners) is the fallback. In both branches a window blur closes the colour picker (a click in the preview iframe never reaches the admin document, and light dismiss does not see it), and the engine dropdown keeps its focus guard. The admin's top-bar menus (`.tool-pop`, the settings popover) use `position: absolute`: the top bar does not scroll. The accordion's smooth height is `::details-content` + `interpolate-size` behind `@supports`, and scroll-linked effects use `animation-timeline: scroll()/view()`.
- **The panel language's class contract (ADR-0016):** panel heading `.panel-strong`; control row `.ctl-row` (flex, label left / control right), toggle rows `.gridmenu-snap` (text left, toggle at the far right), value readouts `.gridmenu-value` (tabular-nums); collapsible group `<details class="group">` with `.group-items` inside, an open group marked with an accent border, section folders without a pill frame as the `.frame-group` variant; segment control `.seg` with the `.on` state; mini label `.mini-label` (small uppercase with letter-spacing); chip `.chip` (999px pill in currentColor, muted) with the `.accent` variant for the active choice; preview surface `.sample` (muted surface with a thin border and radius); empty state and errors `.panel-hint`, with the `.place-error` pattern. The panel markup lives in `editor/src/App.svelte`.
- **The editor's own ids (ADR-0021):** the site themes' preset ids are English (well, stone, plum, ocean, night, with the `themePreset.*` keys in all five dictionaries) and are never persisted, since the active preset is derived from the stored tokens. The admin themes' ids (purple, well, gold, grey, aurora, dusk, ember) are persisted only in the browser's localStorage under `urd-admin-theme` and are migrated on read, as the draft keys are: the editor reads the old key when the new one is missing, writes the new key and deletes the old one, so no browser draft is lost. Custom CSS written by a site owner against old class names (`urd-handlekurv-*`, `urd-produkt-*` and the like) has to be updated to the English class names; the classes are runtime-generated and never persisted.
- **The preview's Screen device (ADR-0018):** the mode (My window or Editing size, with the editing width and optional height) is kept per browser in localStorage under `urd-admin-screen`, read and written by `editor/src/lib/own-screen.js`. The binding limit of the content width (`contentWidth / (1 - 2 * gutter / 100)`) is the pure function `bindingWidth` in `editor/src/lib/content-width.js`, with its own test; the Site panel shows the width as four quick choices plus free adjustment from 960 to 1920, the side margin as a scale (None, Small, Medium, Large) with the raw vw number under Advanced, and a live sample against three real screen widths showing where the width binds.
- **The editor measures the canvas, never the section:** every geometry site in `preview-edit.js` (drag, resize, arrow keys, marquee, group drag, grid overlay, block menu, materialisation of mobile frames) takes its width from the shared `canvasOf` helper, so a forgotten measurement is mechanically searchable. `sticky.js` derives the block's left edge and width from the canvas rect and the release limit from the section's top and bottom, in separate variables; it reads the left edge with `parseFloat(el.style.left)`, so the inline `left` must stay a plain percentage (a `calc()` string yields NaN), which is one reason the content width is a canvas node and not a `calc()` in `frameToCss`.

### The editor's parts (0.7.26)

Recorded before the split, 14 October 2026: `editor/src/App.svelte` held the whole editor in one file of 14,676 lines (the script to line 6928, the markup to line 11699, the CSS to the end) with 109 `$state` and 41 `$derived` declarations, 28 effects, 420 functions, 58 snippets and the twelve panels as branches on `activePanel`. The build (`npm run build`: Vite 8.3, vite-plugin-svelte 7.3, Svelte 5.57) took 9 m 31 s on the development machine, of which 573 s was the Svelte compile of this one file, and every family added to the element menu made it longer. The split gives every part one job, lets the compiler work file by file, and changes nothing a site owner sees.

**The parts and what they own.** A part reads the state it shows and writes only through the functions of the module that owns the state; the state a part alone uses (a panel's own fields, a drag in progress) stays inside the part.

**The state modules** (`editor/src/state/`, since 0.7.26.5). Each `.svelte.js` module holds its state as module-level `$state` and `$derived` with the functions that change it, and exports two things: a handle, `<name>State`, with a getter and a setter for every variable and its functions and constants as they are, and `effects()`, the module's `$effect` blocks, which the shell runs once at its start. Inside a module the names are bare; another module reaches them through the handle (`pageState.selectedBlock`), never through a copy, so every piece of state has one owner and a read follows it. The modules import each other freely; a read of another handle at load time would meet the import cycle, so loads read nothing across modules (tests/app-render.test.mjs loads them all).

**The CSS.** The admin's stylesheet is global, in `editor/src/app.css`, imported by `main.js` after the components so that it wins a tie with a lib component's rule as it did when its specificity was one class higher. It moved out of App.svelte as one block in its order (0.7.26.2), with the `:global()` wrappers unwrapped, so the cascade among its own rules stays as it was, and a rule whose subject is a form element, a `.ghost` or a `.primary` carries a guard that keeps it out of the lib components (`Dropdown`, `ColorPicker`, `GlyphPicker`, `MarkPicker`, `DesignPicker`, `IconEditor`, `Choice`), which draw their own controls and were never reached by the scoped rules. ## The publishing flow (`template/functions/`)

Cloudflare Pages Functions - small serverless functions that ship with the repo and require zero operations ([ADR-0003](adr/0003-publishing-via-github-oauth-and-pages-functions.md)). The pattern is validated in production in ApeironLF.

| Endpoint | Role |
|---|---|
| `GET /api/github/login` | Starts GitHub OAuth (state cookie against CSRF) |
| `GET /api/github/callback` | Exchanges the code for a token server-side; the token is stored in an httpOnly cookie and never reaches browser JS |
| `GET /api/github/me` | Login status + enforces `ALLOWED_LOGINS` |
| `POST /api/github/commit` | The core: commits all changed files as ONE commit via the Git Data API |
| `GET /api/github/latest` | HEAD + diff since the baseline SHA → conflict detection («Someone else has published») |
| `GET /api/github/history` | Latest commits → basis for undoing a publish |
| `POST /api/github/revert` | Forward revert: a new commit pointing at the previous tree - history is never deleted |

Security layers (defence in depth):

1. **No admin password** - *editing* locally is harmless; the gate is that only GitHub-logged-in users in `ALLOWED_LOGINS` can *commit*.
2. **Path allowlist in `guard.js`:** publishing can only write `content/**` (json, css, xml), `media/**` (image, audio and video extensions), `plugins/plugins.json`, the visibility files `sitemap.xml` and `robots.txt`, and per-page routing copies (`<slug>/index.html`, never reserved folders) - never `functions/**`, `.github/**`, `admin/**`, `assets/engine/**`, `assets/urd/**`, `_headers`, `_redirects`, `urd.json`, the root `index.html`, `404.html`, `.gitignore` or `wrangler.toml`. A hijacked editor session therefore cannot plant code. The `commit` endpoint takes `{message, files:[{path,content,encoding}]}` and creates one commit through the Git Data API: blobs, then a tree, then a commit, then the ref is moved; `latest?base=<sha>` returns whether other people have published since the editor loaded (the base SHA the draft was built on).
3. **Conflict guard in two layers:** the editor compares against the baseline SHA (`latest?base=`) and warns on overlapping files; the commit endpoint additionally rejects with 409 if HEAD has moved since the check (optional `expect` in the request). Without `expect` (older clients, direct API use) the server-side guard does not exist.

Configuration is six environment variables at the host: `GITHUB_REPO`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_BRANCH`, `GITHUB_SCOPE`, `ALLOWED_LOGINS`.

### The payment layer (ADR-0020)

The checkout function creates the Vipps session with `returnUrl` set to the checkout page with `?ordered=1`; on that query the checkout block shows a receipt and empties the cart. The callback endpoint `/api/vipps/callback` acknowledges 200 and stores nothing: the orders live in the Vipps portal (the order lines are sent along in the session), and the site has no order database. `functions/_lib/vipps.js` owns the pure logic (payload validation, conversion to øre, the session body) and is tested in node; `functions/api/vipps/checkout.js` and `functions/api/vipps/callback.js` are thin shells around it. The secrets it needs are listed in [DEVELOPMENT-en-GB.md](languages/DEVELOPMENT-en-GB.md#common-tasks).

```

├── editor/        Svelte source code - does NOT ship with cloned sites
└── template/      THE SITE. Deployed as the Pages root; this is what associations clone.
```

In early development the schema, engine and editor change in the same commit, and the built editor in `template/admin/assets/` must always match the engine from the same commit - hence one repo for now ([ADR-0004](adr/0004-monorepo-with-template-folder.md)). At every release the release Action (`.github/workflows/release.yml`) syncs the contents of `template/` to the clean `urd-template` repo («Use this template») as one squashed commit, tagged with the version.

## Engine versioning (ADR-0013)

The engine lives in a versioned folder, `template/assets/engine/<version>/`, where the folder name is always equal to the `engine` field in urd.json (test-enforced). This makes the whole import graph addressable per version (relative ES imports inherit no `?v=` query), so the template's `_headers` can give `/assets/engine/*` immutable caching with a version-neutral rule that never needs changing. The monorepo's `template/_headers` revalidates the engine instead (`no-cache`), since its files change between releases under the same folder, and the release sync writes the template's rule (`scripts/release-headers.mjs`, ADR-0013 decision 2). The stable plugin API lives in `template/assets/urd/`: shell modules (i18n, hint, dropdown and others) that re-export from the current version and are revalidated normally - plugins never hard-code the versioned path. Any mechanism that switches the engine version (phase releases, the updater) writes the root index.html and all `<slug>/index.html` copies in the same commit (the copy-refresh duty).

The dynamic imports in the engine's `i18n.js` and `plugins.js` (admin dictionaries, language packs) go through the `/assets/urd/` shells, not relative paths, because the same lines run from the editor bundle, where a relative path would resolve against the bundle's location.

## The update mechanism (ADR-0014)

`template/urd.json` is the manifest: engine version + the ownership map (`ownedPaths` for Urd-owned paths, `userPaths` for `content/**`, `media/**`, `plugins/**`). The Updates panel in admin checks against the `urd-template` repo via `/api/github/update`: the user's git tree is compared with the template's tree at the BASELINE (the tag `v<engine>` for the version the site is running) and at the target version, using pure blob-SHA comparisons - an equal SHA is identical content, so «hand-edited» is decided without loading a single file. Execution writes the Urd-owned files as ONE atomic commit (inline trees, expect guard): the engine atom group is always switched as a whole, optional files (functions, loose root files) can be held back per file, `_headers` is never written (a diff instruction instead, cf. ADR-0006), and user-owned paths are never touched. Content written on an old schema is lifted by the migration contract at load time; that is the whole point of it.

The updater is `functions/api/github/update.js`: GET runs the check, POST performs the update, and both open with the same `requirePublisher` prologue as publishing. `guard.js` holds the ownership map `OWNED_PATTERNS` / `USER_PATTERNS`, mirroring `ownedPaths` / `userPaths` in urd.json and contract-tested against it, with the predicates `isOwnedPath` / `isUserPath`; a completeness test requires that every actual file in the template matches exactly one ownership class. The perform step fetches all target texts in ONE GraphQL call (`Blob.text` via aliases), builds the Git tree with inline `content` (never one blob POST per file), chunked into chained `base_tree` trees for large volumes, and commits with `expect` protection (409 when HEAD has moved). Binary and truncated blobs take the REST detour (base64 from the template repo straight in as a blob in the user's repo, two subrequests each), at most `BLOB_BATCH` (18) per call: ONE GraphQL call first tells which target files are such blobs and which of them the user's repo already holds (`object(oid:)` on the user's repo; pure `blobBatch` in update-plan.js picks the next batch), a call that copies a batch answers 429 `updateContinue` with `copied` and `total`, and the Updates panel repeats the call while it copies more, until a call that finds at most `BLOB_ROOM` (10) left copies those and commits with the tree referring to them by the template's SHAs, so an update with few such files is one call as before. The subrequest budget is about 8 for the check, about 43 for a copying call and at most about 33 for the committing one, under the cap of 50 on the free plan; a call that goes over keeps what it copied, and the next one goes on from there. The error codes are `api.update*` keys in all five admin dictionaries, enforced by the i18n contract test.

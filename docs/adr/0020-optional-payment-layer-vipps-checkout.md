# ADR-0020: Optional payment layer via the Vipps MobilePay ePayment API (hosted redirect)

Date: 25 August 2026
Status: Accepted; decision 6 amended 19 October 2026 (a members' code of ADR-0027 may make the member price chargeable), earlier text in [amended/](amended/0020-optional-payment-layer-vipps-checkout-until-2026-10-19.md); decision 1 amended 20 October 2026 (the order button named by its role, since its text follows angrerettloven § 16), earlier text in [amended/](amended/0020-optional-payment-layer-vipps-checkout-until-2026-10-20.md); decision 4 amended 22 October 2026 (the return empties the cart only for a session the site's own endpoint confirms paid), earlier text in [amended/](amended/0020-optional-payment-layer-vipps-checkout-until-2026-10-22.md); the provider and decisions 3, 4 and 5 amended 23 October 2026 (the layer moved from Vipps Checkout, which ends on 30 April 2027, to the ePayment API: the payment reserved and captured when the goods ship, the contact details shared from the app, the order lines on the receipt, a signed webhook), earlier text in [amended/](amended/0020-optional-payment-layer-vipps-checkout-until-2026-10-23.md)

## Context

Milestone 0.7.5 promises a real payment checkout as an OPTIONAL layer on top of the order-form checkout; the form checkout remains the default, and the core remains gateway-free. The backlog named two candidates: the Snipcart model (git-owned catalogue + third-party cart/checkout via CSP opt-in) and Vipps Checkout via a Pages Function.

The layer was first built on Vipps Checkout (checkout/v3). Vipps MobilePay sold Checkout to Kustom in June 2026, and Kustom discontinues it on 30 April 2027. The two candidates for the move were the Vipps MobilePay ePayment API and Kustom Checkout; the survey «What a shop needs» (19 October 2026, [SURVEYS.md](../comparison/SURVEYS.md)) read both against what the shop of [ADR-0027](0027-a-shop-without-a-database.md) needs from the layer: a reservation captured when the goods ship, order lines on the receipt, signed webhooks and a fixed list of shipping options.

## Decision

The payment layer is built on **the Vipps MobilePay ePayment API via a dedicated Pages Function with hosted redirect**:

1. The checkout block gets the additive prop `vippsCheckout` (bool, default false). When set, it shows a button beside the form's order button that names the payment by its role («Pay with Vipps»), since its text follows angrerettloven § 16 like the order button's.
2. The button POSTs the cart lines (id/quantity/variant) and the contact fields to the site's own function `/api/vipps/checkout`. The function ALWAYS recomputes the total from the git-owned catalogue (`content/samlinger/`, kind `products`) - the client's amount is never used. An unknown product id or a manipulated payload is rejected.
3. The function creates a payment at Vipps (`POST /epayment/v1/payments`: a wallet payment through the web redirect, the payment's reference as the idempotency key) and responds with the address Vipps answers with; the client opens it unchanged. The payment happens at Vipps, never on the site. The amount is reserved, and the seller captures it in the Vipps portal when the goods ship, within the 180 days Norway allows; the regulation forbids capture before the goods are ready, and the site's own function captures nothing before the shop of v1.1 ([ADR-0027](0027-a-shop-without-a-database.md) decision 4). The payment asks the buyer to share the name, the email and the phone from the app (the profile scope), so the form's contact fields may stay empty; the address joins the scope with shipping in v1.1. The order lines and the typed contact fields go in the payment's description, read in the Vipps portal, and the lines go as the receipt in the buyer's app when the seller stands outside the VAT register (the lines carry no tax; the VAT lines come with the shop of v1.1).
4. On return the checkout block asks the site's session endpoint, which reads the payment's state and the shared contact details from Vipps, and for a reserved payment shows a receipt that thanks the buyer by name and empties the cart. The webhook endpoint takes the payment events of a registration the site owner makes, checks that the delivery is signed with the registration's secret (HMAC-SHA256 over the method, the path, the date, the host and the body's hash), and stores nothing - the orders live in the Vipps portal, the site is static and has no order database.
5. Configuration is Cloudflare secrets, never repo data: the sales unit's client id, client secret, subscription key and serial number, the optional API base for the test environment, and the optional webhook secret. Without the four the function reports that Vipps is not configured, the button shows a calm unavailable text, and the form checkout works unchanged.
6. The member price is a displayed second price on a trust basis (login is outside the core, BACKLOG); the payment layer charges the regular price, unless the buyer enters a members' discount code of [ADR-0027](0027-a-shop-without-a-database.md), which makes the member price chargeable.

## Rationale

- **The target audience is Norwegian.** The Vipps-number instruction is already the manual payment route; a Vipps payment is the same payment relationship with real completion. The site owner only needs their Vipps MobilePay agreement and to paste four secrets into Cloudflare.
- **The CSP remains untouched.** Hosted redirect means no third-party script, no iframe and no connect-src extension on the site (the ADR-0006 friction is avoided entirely). Sensitive calls happen server-side in the function, which owns the secrets.
- **The ePayment API over Kustom Checkout:** the same four secrets as before and the same hosted redirect; Kustom Checkout is an embedded frame by default (its hosts in the CSP), and its hosted page is onboarded by invitation with no public prices. Kustom authorises for about 28 days, the ePayment API for 180 in Norway, so the reservation outlives a club's shipping time. The ePayment API gives all four things the shop of v1.1 needs: capture at shipping, order lines on the receipt, signed webhooks, and Express with fixed shipping options.
- **The payment methods of the two candidates** (read 23 October 2026): the ePayment API pays through the Vipps and MobilePay apps, and offers freestanding card payments with 3D Secure in Norway through the same create call (`paymentMethod.type: 'CARD'`), which the test environment does not cover; it offers neither Apple Pay nor Google Pay. Kustom Checkout lists card, Apple Pay, Google Pay, Vipps and MobilePay among its methods. Urd takes the wallet payment: its buyers are Norwegian and pay with Vipps, the card path is one field away and is weighed with the shop of v1.1, and Apple Pay and Google Pay would need Kustom's frame, which the CSP decision rules out.
- **Snipcart rejected:** injects its own cart and checkout UI that duplicates Urd's cart/checkout (two carts on the same site), requires a CDN script + API host in the CSP, and costs a subscription/transaction fee. The model suits sites WITHOUT their own cart; Urd has one.
- **Prices are validated server-side** because the cart lives with the visitor (localStorage) and anything the client sends may have been tampered with; the catalogue in git is the source of truth.

## Consequences

- The pure logic (payload validation, conversion to øre, the payment body, the receipt lines, the reading of a payment's state, the token cache and the webhook signature) is one module under `functions/_lib/` and is tested in node; the network side (the access token kept in the isolate until shortly before it expires, one call shape with the common headers and a timeout) is a second module beside it, and the three endpoints (the payment's creation, its state, the webhook) are thin shells.
- The form checkout and the payment button live side by side; no part of the core gains a dependency on Vipps.
- The seller captures by hand in the Vipps portal until the shop of v1.1 captures from the site at shipping; a reservation not captured within the window is released by Vipps.
- A test payment (the Done-when criterion) requires the site owner's test sales unit, the test app and a test user on a deployed site, with the API base pointed at the test environment; locally the button degrades gracefully. The setup guide walks through it.
- If the provider is switched later, the surface is small: one block prop, three functions, one network helper and one pure module.

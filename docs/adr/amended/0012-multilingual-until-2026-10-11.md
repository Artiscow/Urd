# ADR-0012: Multilingual via pure ES module locales, two registries and native Intl

Date: 3 August 2026. Status: accepted (v0.6, milestone 0.6.8); addendum on core languages (August 2026).

## Context

The engine is dependency-free vanilla JS served raw; the editor is Svelte with a build, and the bundle is committed. All user-visible text was hardcoded Norwegian at the point of use (~1000+ distinct strings). The target languages are Bokmål (nb), Nynorsk (nn), British English (en-GB), Northern Sami (se) and Turkish (tr), with more as community contributions later. Research on Shopify (storefront/schema locale files), Squarespace (one site language for built-in chrome), Publii (app locales + language file checker), Ghost ({{t}} + locales JSON) and WordPress (gettext) informed the choices.

## Decision

1. **Pure ES module locales, no library, no build.** The language files are hand-written ES modules under `template/assets/engine/locales/` (`site/` for visitor texts, `admin/` for the admin chrome) and `template/plugins/<id>/locales/` for plugins. They can be imported directly by the engine, the editor and node tests. Compiler-based solutions (Paraglide) and runtime libraries (i18next, gettext/ICU) are rejected: the engine cannot have dependencies or a build, and a translation PR must be a pure file change without a rebuild.
2. **Keys are English identifiers** with dotted namespaces (`nav.toTop`, `footer.newsletter.invalidEmail`) - the form of the locale files is a data contract (AGENTS.md). Source-string-as-key (the Ghost/WordPress model) is rejected for the same reason.
3. **Two registries in `engine/i18n.js`:** `t()` for visitor texts follows `site.lang` (matched via `matchLang`; 'no' and all nb variants are Bokmål, Southern/Lule Sami fall to Northern Sami; a code without a match is looked up among the language packs before falling to nb). `ta()` for the admin chrome follows the admin language (localStorage `urd-admin-lang`; auto from `navigator.languages` when the key is missing, explicit choice wins - the same order as i18next-browser-languagedetector). The visitor chrome NEVER auto-detects: it must be consistent with the content, which has one language (the Squarespace model).
4. **nb is always the static base.** `i18n.js` imports `locales/site/nb.js` statically (preloaded); other languages are dynamically imported in `boot()` after site.json is read, on top of a FRESH copy of the base. A missing key gives the Bokmål text; a completely unknown key gives the key itself (visible, never a crash). The dynamic import is deliberately invisible to the modulepreload contract. `boot()` also sets `document.documentElement.lang` (the shells hardcode "no" only as the pre-JS default).
5. **The admin locales are never bundled:** the editor's main.js imports `/assets/engine/locales/admin/<lang>.js` at runtime before mount, and the preview iframe's canvas chrome does the same lookup itself (shared localStorage, same origin). A language switch is a reload (the Publii model), not live reactivity (~900 call sites).
6. **Date names, plurals and relative time via native Intl (ADR-0011).** Month names/weekdays from `Intl.DateTimeFormat`, relative day counting from `Intl.RelativeTimeFormat`, plurals from `Intl.PluralRules` with key suffixes (`.one`/`.two`/`.other` - Northern Sami has a dual form, so hand-written one/many pairs would have been wrong). ICU has full CLDR data for all five languages; the Bokmål tables in the nb base are the fallback where ICU lacks the language. The calendar's internal time zone Intl (ics.js) is not display and is not touched.
7. **The seed rule:** text that is WRITTEN INTO user data (preset content, block defaults such as 'Les mer', faq seeds) is translated once at insertion with the admin language; visitor rendering never translates user data. Render fallbacks for empty fields (the footer CTA's button text/confirmation) are on the other hand visitor texts: the model layers are language-free, and the `t()` lookup happens in render.
8. **Plugins** get additive manifest fields (`locales: true`, `names` per language) and add their dictionaries via `addSiteDict`/`addAdminDict`, with keys prefixed with the plugin id.
9. **Language packs: new languages come as plugins without code** (0.6.8.10). The manifest field `languages: [{ code, name, site, admin }]` promises `locales/site/<code>.js` and/or `locales/admin/<code>.js` with the engine's OWN keys, and makes `entry`/`provides` optional: a pure language pack is just files. The Bokmål base sits underneath as usual, so a pack can cover one registry or parts of a set. Built-in codes cannot be overridden (a plugin must not be able to hijack Bokmål), and the lookup lives in `engine/language-packs.js`, which is deliberately OUTSIDE the engine's static import closure: it is fetched only when someone actually asks for a language the core does not have, so a site in a built-in language pays nothing for the possibility. The alternative, extending `SUPPORTED_LANGS` for each language, was rejected because it makes every new language an Urd release with a rebuilt editor bundle; here a community can keep its language in its own repo.
10. **The parity test (`tests/i18n.test.mjs`) is the contract:** all language files in all locale sets must have an identical key set to the nb base, no empty values, no em dash, and the same `{var}` tokens per key. It finds the locale directories automatically and is at the same time the «language file checker» tool for contributors (the Publii pattern). Language packs are the exception to the requirement of a FULL set (they may cover parts), but are held to the same rules otherwise, and a key that does not exist in the base is rejected as a typo.

## Consequences

- Translation PRs are pure file changes; the CI parity test catches drift, and no build is required (the admin locales sit outside the bundle).
- A new language = one file per locale set + a matchLang entry; everything else follows. If the language is not to go into Urd itself, a language pack plugin is the way: same files, no core change, no rebuild.
- Non-Norwegian sites pay one extra serial fetch (the site locale) before first render; Norwegian sites pay nothing.
- The Northern Sami translation is a machine-written first draft and must be reviewed by a native speaker (flagged in the files and CONTRIBUTING.md); the parity test ensures form, not content.

## Addendum: the core language model (6 August 2026)

Decided to save delivery time: new keys are kept complete in the CORE LANGUAGES nb, en-GB and tr at every delivery; nn and se are filled in dedicated translation rounds. The runtime was already built for this (missing keys fall to the Bokmål base), so the change is only in the parity test: full parity is enforced for the core languages, while nn/se accept a backlog (reported in the test log) but never unknown keys. Sami was in any case marked «needs native-speaker review».

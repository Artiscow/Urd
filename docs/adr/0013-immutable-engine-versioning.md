# ADR-0013: Immutable engine versioning and the copy-refresh duty

Date: 5 August 2026. Status: accepted (v0.6, milestone 0.6.9); decision 2 amended 7 October 2026, earlier text in [amended/](amended/0013-immutable-engine-versioning-until-2026-10-11.md). How the release writes the headers and what the tests hold is described in [DEVELOPMENT-en-GB.md](../languages/DEVELOPMENT-en-GB.md#releases-automated-from-069).

## Context

The engine is served as raw ES modules, and without cache control every visitor revalidates every module. `?v=` query stamping (the pattern base.css uses) does not work for the engine, because relative ES imports (`import './render.js'`) do not inherit the query from the importer; the only thing that makes the whole graph addressable per version is the path itself. At the same time, publishing writes `<slug>/index.html` routing copies as raw copies of the root index.html, so an engine move that deletes the old directory can orphan copies that are never republished. And plugins (also third-party ones, outside the repo) import engine modules with absolute paths that cannot carry a version number they do not know.

## Decision

1. **The whole engine lives in a versioned directory: `assets/engine/<version>/`, where the directory name is ALWAYS equal to the `engine` field in urd.json.** A separate, cheaper counter is rejected: a forgotten counter bump would silently serve stale immutable modules (mixed engine version in the browser, the worst class of error), while the semver name makes the invariant trivially testable. Everything that needs the directory name reads it from urd.json, so a rename is ONE field change plus git mv.
2. **Immutable caching is true only in a release.** A versioned directory is immutable only where its content never changes under its name. That holds for a released template, not for the monorepo, where the engine's files change between releases under the same directory name; a browser told to keep the modules for a year would mix old and new modules and never start the engine. The released template's `_headers` therefore carries version-neutral immutable rules for `/assets/engine/*` and `/assets/styles/base.css` (the latter always referenced with the content stamp `?v=<hash8>`, the same djb2 hash as the media names), written once and never changed at an engine bump; that is crucial because `_headers` is hand-editable (plugin CSP, ADR-0006) and permanently exempt from automatic updating. The monorepo's `template/_headers` revalidates the engine instead (`Cache-Control: no-cache`: the browser asks before every use, and an unchanged file costs a 304 with no content), which reaches the test site and a local Pages dev server. The release writes the template's immutable rule into its copy of `_headers`, and stops unless the copy carries it. Released and published sites keep the rule they have, and the updater never writes `_headers` (ADR-0014).
3. **The stable plugin API lives in `assets/urd/`, OUTSIDE the immutable tree:** shell modules (one re-export each) for i18n.js, hint.js, dropdown.js, language-packs.js and locales/admin/<code>.js x5. Plugins import ONLY `/assets/urd/` paths and never hardcode the versioned path. The shells are revalidated normally (no immutable), carry the version in the re-export target and are updated in the release ritual. Since both the engine's relative imports and the shells end at the same versioned module URL, the module instance is shared: the i18n registries remain singletons. The alternatives were rejected: an importmap requires an inline script (the CSP deliberately does not have `unsafe-inline`), and shells at the engine root would have required a VERSIONED immutable rule in the hand-editable `_headers`.
4. **The copy-refresh duty:** any mechanism that switches engine version MUST write the root index.html and ALL `<slug>/index.html` copies in the same commit as the directory switch, and the copies in the template are byte-identical to the root. Publishing does this (the copies are written as raw copies of the served root at every publish), and the updater (ADR-0014) is explicitly obliged to do so.
5. **Clean swap without N-1 retention:** the old engine directory is deleted in the same commit as the new one is added. The window where an already downloaded HTML points to a deleted directory is seconds (the deploy atom at Cloudflare Pages is the whole deploy), and a reload fetches the new shell; keeping N-1 for one round would have doubled the repo size and deferred, not removed, the problem. The trade-off is accepted for v1 of the updater.

## Consequences

- An engine switch is a release action (phase release/updater), never an ongoing development action; local development and preview are unaffected (the paths are the same, just versioned).
- Conditional per-page asset loading (former ELEMENTKART 5b.7, now in [CODE.md](../comparison/CODE.md#part-6-what-to-take)) is explicitly deferred: per-page-varying shells stand in direct tension with both the global modulepreload list (the anti-drift test) and the copy-refresh duty (the copies must be byte-identical). If it is taken up again, it must solve both.
- New engine modules that are to be plugin API require a new shell in `assets/urd/` and a line in the plugin README; everything else in the engine is internals and can be moved freely within the version directory.
- A change of the template's `_headers` text reaches every site that never edited the file: the updater shows a «change by hand» note when a site's `_headers` differs from the template's at the target version.
- The window of decision 5 is longer than seconds for a page held from before an update (a document prefetched by the speculation rules, a back/forward-cache restore, an open tab's lazy import), which can load files from the deleted directory. A recovery in the page (a boot guard that refetches the files the page names and reloads once) is open in BACKLOG under the updater hardening, since it would ship with the releases.

## Addendum, 22 October 2026: the link resolver as a shell

`links.js` joined the shells of decision 3 in 0.7.27.8: it re-exports `resolveLink` and `linkAttrs` from nav-model.js, so a plugin draws its `link` field as the core blocks draw their links. It is the new shell the consequence on new plugin API calls for, and no decision changes.

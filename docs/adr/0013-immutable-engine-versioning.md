# ADR-0013: Immutable engine versioning and the copy-refresh duty

Date: 5 August 2026. Status: accepted (v0.6, milestone 0.6.9).

## Context

The engine was served as raw ES modules without cache control: every visitor revalidated every module, and the 0.6.32 performance work deferred immutable caching to here. `?v=` query stamping (the pattern base.css now uses) does not work for the engine, because relative ES imports (`import './render.js'`) do not inherit the query from the importer; the only thing that makes the whole graph addressable per version is the path itself. At the same time, publishing writes `<slug>/index.html` routing copies as raw copies of the root index.html, so an engine move that deletes the old directory can orphan copies that are never republished. And plugins (also third-party ones, outside the repo) import engine modules with absolute paths that cannot carry a version number they do not know.

## Decision

1. **The whole engine lives in a versioned directory: `assets/engine/<version>/`, where the directory name is ALWAYS equal to the `engine` field in urd.json.** A separate, cheaper counter is rejected: a forgotten counter bump would silently serve stale immutable modules (mixed engine version in the browser, the worst class of error), while the semver name makes the invariant trivially testable. The tests, the editor build and the validation read the directory name from urd.json (tests/_engine.mjs, the vite alias `$engine`, validate.mjs), so a rename is ONE field change plus git mv; the modulepreload test enforces that the directory exists, that only one version exists, and that all HTML references point to it.
2. **`_headers` gets version-neutral immutable rules:** `/assets/engine/*` and `/assets/styles/base.css` (the latter always referenced with the content stamp `?v=<hash8>`, the same djb2 hash as the media names). The rules are written ONCE and never need changing at an engine bump; that is crucial because `_headers` is hand-editable (plugin CSP, ADR-0006) and permanently exempt from automatic updating.
3. **The stable plugin API lives in `assets/urd/`, OUTSIDE the immutable tree:** shell modules (one re-export each) for i18n.js, hint.js, dropdown.js, language-packs.js and locales/admin/<code>.js x5. Plugins import ONLY `/assets/urd/` paths and never hardcode the versioned path. The shells are revalidated normally (no immutable), carry the version in the re-export target and are updated in the release ritual (test-enforced against urd.json.engine). Since both the engine's relative imports and the shells end at the same versioned module URL, the module instance is shared: the i18n registries remain singletons. The dynamic imports in i18n.js/plugins.js (admin dictionaries, language packs) also go via the shells, because the same lines run from the editor bundle, where a relative path would point to the wrong place. The alternatives were rejected: an importmap requires an inline script (the CSP deliberately does not have `unsafe-inline`), and shells at the engine root would have required a VERSIONED immutable rule in the hand-editable `_headers`.
4. **The copy-refresh duty:** any mechanism that switches engine version MUST write the root index.html and ALL `<slug>/index.html` copies in the same commit as the directory switch. Publishing already does this (the copies are written as raw copies of the served root at every publish); the 0.6.9 updater is explicitly obliged to do so. The modulepreload test requires that the copies in the template are byte-identical to the root, after drift was found in practice (the copies lacked the theme.css link and theme-init.js).
5. **Clean swap without N-1 retention:** the old engine directory is deleted in the same commit as the new one is added. The window where an already downloaded HTML points to a deleted directory is seconds (the deploy atom at Cloudflare Pages is the whole deploy), and a reload fetches the new shell; keeping N-1 for one round would have doubled the repo size and deferred, not removed, the problem. The trade-off is accepted for v1 of the updater.

## Consequences

- An engine switch is a release action (phase release/updater), never an ongoing development action; local development and preview are unaffected (the paths are the same, just versioned).
- ELEMENTKART 5b.7 (conditional per-page asset loading) is explicitly deferred: per-page-varying shells stand in direct tension with both the global modulepreload list (the anti-drift test) and the copy-refresh duty (the copies must be byte-identical). If it is taken up again, it must solve both.
- New engine modules that are to be plugin API require a new shell in `assets/urd/` and a line in the plugin README; everything else in the engine is internals and can be moved freely within the version directory.
- The editor bundle bundles engine modules and must be rebuilt at an engine bump (the bundler's source comments carry the path), which the release ritual requires anyway.

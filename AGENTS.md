# Urd: guidance for coding agents

This file is loaded automatically in every session (Claude Code loads it via the `@` import in `CLAUDE.md`; tools that follow the AGENTS.md standard read it directly). It pins the durable rules and points to the authoritative documents. Read it before making changes.

## What Urd is

Urd is a dependency-free static site builder where the cloned repo IS the website, and `/admin` is the WYSIWYG editor. The engine is pure, readable vanilla JS (served raw, no build step). The editor is Svelte 5 (runes) and is built into `template/admin/assets/`. Publishing goes through GitHub OAuth + Cloudflare Pages Functions. At releases, `template/` is synced as one squashed commit to the template repo `urd-template` («Use this template»), and deployed sites fetch new versions with the Updates panel in admin (ADR-0014).

**The two-tier model (ADR-0001):** the editor shows the REAL site in an iframe (`?preview=1`) and drives it via postMessage. The preview IS production: same engine, same render. The editor owns the draft; the engine renders it. The messages (`urd-edit`, `urd-move`, `urd-grow`, `urd-add-block`, ...) are the contract between them.

**When you pick up work:** read [docs/CHANGELOG.md](docs/CHANGELOG.md) for the latest state, [docs/BACKLOG.md](docs/BACKLOG.md) for what comes next, and [docs/TESTRUNDER.md](docs/TESTRUNDER.md) for the test-round checklist. Full orientation: [docs/VEIKART.md](docs/VEIKART.md) (phases and goals), [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), [docs/SCHEMA.md](docs/SCHEMA.md) (the data contract), [docs/UTVIKLING.md](docs/UTVIKLING.md) (technical rules), [docs/sammenligning/](docs/sammenligning/) (the feature, element and lessons maps against other builders), [CONTRIBUTING.md](CONTRIBUTING.md), and the ADRs in [docs/adr/](docs/adr/).

## Repo structure

- `template/` is the deployable site, synced to the `urd-template` repo at releases. `template/assets/engine/<version>/` is the engine (vanilla JS, served raw; the directory name is ALWAYS equal to the `engine` field in `template/urd.json`, ADR-0013). `template/assets/urd/` holds the stable plugin API shells (re-exports against the current engine version; the only thing plugins may import). `template/urd.json` is the version and ownership contract (`engine`, `ownedPaths`, `userPaths`). `template/functions/` is the Cloudflare Pages Functions, `template/plugins/` is the plugins, `template/content/` is user data, `template/readme/` holds the template's README translations (the root is English).
- `editor/src/` is the Svelte 5 admin. Built with `cd editor && npm run build` into `template/admin/assets/editor.js` + `editor.css`. The committed bundle MUST match the source (CI checks it). Engine imports go through the `$engine` alias (vite.config.js reads the directory name from urd.json).
- `tests/` holds the `node --test` tests (engine, guards, contract and file invariants). Engine modules are loaded via `tests/_engine.mjs` (`await engineImport(...)`), never with a static path. `schema/` holds the JSON schemas, `scripts/` the release tooling (check-release.mjs), `.github/workflows/` CI + the release sync, `dev-server.py` the local server, and `docs/` the documentation.

## Verification: always before anything is «done»

Run all three, and report the result honestly:

1. Build the editor: `cd editor && npm run build`
2. Tests: `node --test tests/*.mjs` (must be green)
3. Schema validation: `cd editor && npm run validate`

If you change `editor/src/`, you must rebuild and commit the bundle (otherwise CI's build-conformity check fails). IMPORTANT: the editor IMPORTS AND BUNDLES several engine modules (see the imports in `editor/src/App.svelte`, `editor/src/main.js` and `editor/src/lib/*.svelte`; find them with `grep -rn -F '$engine/' editor/src`: `migrate`, `plugins`, `i18n`, `sections/presets`, `templates-model`, `palette-search`, `page-presets`, `preset-thumb`, `backgrounds/*`, `animations/core`, `theme`, `imageTools`, `fonts`, `place`, `icons`, `glyphs`, `footer-thumb`, `collections-csv`, `feeds`, `anchored`), so a change in ANY OF THESE must also be rebuilt and committed - «no build step» applies only to engine files the editor does not import (e.g. `render.js`, `nav.js`, `lightbox.js`, most of `blocks/*`). If in doubt: build, and `git diff -- template/admin/assets` shows whether the bundle was touched.

If CI's build-conformity check fails with a diff inside framework code (the Svelte runtime, not app code), it is dependency drift: check that `node_modules/svelte/package.json` matches the version in `editor/package-lock.json`, and run `rm -rf node_modules && npm ci` + a new build if not (historical event 22 July 2026: npm delivered 5.56.5 where the lockfile pinned 5.56.7). The bundle fix must be pushed together with the source it was built from.

**The scope of verification follows the diff** (rule set 3 August 2026):

- **Intermediate commits along the way** need no full round: run only the tests that cover what you touch (e.g. `node --test tests/guard.test.mjs`), or none. The whole ritual belongs to push preparation, not to every commit. Every commit is still numbered (see Versioning under Workflow).
- **A push with docs-only changes (.md):** an editor rebuild is unnecessary (markdown cannot affect the bundle), and the independent review step can be replaced by mechanical checks: em dash, checkbox syntax, link targets, version-number consistency, and that nothing was removed from TESTRUNDER (precedent: 0.6.34). The full test suite costs seconds and may well be run, but CI runs the same checks after the push anyway. Exception: if the diff touches `docs/SCHEMA.md`, it is never docs-only - the three-places rule requires SCHEMA.md to change in the same commit as `schema/` and the example data, so a bare SCHEMA.md diff is a half-done schema change and gets the full round.
- **A push with code, schema or content changes:** the full round as described above: build + all tests + schema validation + independent review.

CI runs the same three plus the build-conformity check (tests.yml), CodeQL scans on push and weekly, dependency-review runs on PRs, and release.yml syncs template/ to the template repo at releases, gated by `scripts/check-release.mjs`. Two recurring CodeQL pitfalls: (1) never check a URL with a substring (`.includes('vert.no')`), parse the URL and compare the host exactly; (2) use anchored regexes for URL and data validation, which CodeQL recognises as barriers.

**At a release, a fourth step applies:** `node scripts/check-release.mjs v<version>` must be green in full mode (tag == `urd.json.engine` == CHANGELOG release heading == `editor/package.json`, and the engine directory exists) BEFORE anything is tagged.

## Non-negotiable rules

- **The invariant: an Urd update must NEVER break a built site.** If you change the props shape of a block, section, background or animation: bump `version`, write a migration, add a test. See ADR-0005. Before v1, unpushed format changes need no migration, and the pre-v1 migrations are baked in (ADR-0005 addendum); from v1.0 the contract is fully enforced.
- **All schema fields are additive.** Never remove a field without a migration.
- **Schema changes are made in three places in the same commit:** `docs/SCHEMA.md`, `schema/`, and the example data.
- **`_headers` is Urd-owned, never written by publishing** (ADR-0006) **and is PERMANENTLY exempt from the updater**, which shows diff instructions instead (ADR-0014). Plugins declare CSP needs in the manifest; the host is added manually to `_headers` in the repo. `_redirects` is publishing-generated (built in v0.7) and sits in the guard's DENY until then (ADR-0015).
- **Every file in `template/` has exactly ONE ownership class** (`ownedPaths`/`userPaths` in urd.json, mirrored in guard.js; the contract and completeness tests enforce it). New file = classify it in the same commit; use `<folder>/**` patterns so additions do not require a contract change. The engine atom group (assets, admin, index.html, slug copies, urd.json) can never be split in the update.
- **Reserved slugs are maintained in two places** (the publishing guard AND the editor's RESERVED_SLUGS), and a slug reservation after v1 requires a clean-up path in the updater.

## Workflow

- **The message «commit» closes a work round:** the commit entry is then written in CHANGELOG for everything done that round, the backlog (and TESTRUNDER on delivery) is updated, and a numbered commit message is proposed (message text only, no git commands). The scope of verification follows the diff (see Verification). **The message «push» triggers push preparation:** full verification, independent review (or mechanical checks when docs-only), a rebuild if the diff requires it, and the p-entry in CHANGELOG. Pushing is done manually (GitHub Desktop), never by the agent; do not commit or push yourself.
- **The message «release» (or «push og release») triggers the release ritual IN ADDITION to push preparation:** the engine version is bumped following the UTVIKLING ritual (the engine field in urd.json, git mv of the engine directory to `assets/engine/<new version>/`, the re-export targets in the `assets/urd/` shells, the HTML shells' references, a rebuilt bundle, the CHANGELOG release heading `## [x.y.z]` and editor/package.json), and check-release must be green in FULL mode before the commit message is proposed. Tagging and the GitHub release are always done manually by the repo owner AFTER the push (tag last, never first): a new tag alone is never a new version, and a failed release is cleaned up by deleting both the release and the tag before a new attempt. The template repo's tag is the updater's checksum baseline and is NEVER moved.
- **Independent review before the commit proposal:** let a fresh agent without the session's context review the whole diff against the rules in this file and the ADRs, and fix real findings. The session that wrote the changes must never be the only one that assessed them. Then a numbered commit message is proposed (message text only, no git commands).
- **Versioning (commit = code building, push = test delivery):** commits are numbered in ascending order; each entry inherits the number of the backlog item the work belongs under, plus one digit for order; work without a milestone belongs under the phase's standing «Løpende» item (0.6.0.x), and flat phase numbers are no longer handed out (the convention is described in the CHANGELOG introduction and not repeated here). The order digit is added only when the milestone actually gets more than one commit: if the whole milestone lands in one commit, the commit number is the milestone's own number (0.7.1, not 0.7.1.1). If the milestone later has to be reopened, the new commits are numbered 0.7.1.2, 0.7.1.3 and so on, so the flat number reads as 0.7.1.1. The exception is the phase's standing Løpende item, which is always four-part (0.7.0.x) since it never closes. Along the way, several small commits can be made without full ceremony; the scope of verification follows the diff (see Verification). The last commit in a push is the push preparation (where the p-entry is written; commit entries, backlog and TESTRUNDER have all been updated continuously at every commit), and the push inherits the commit span since the previous push with a p suffix: one commit 0.6.0.4 gives 0.6.0.4p, several commits 0.6.7.2 to 0.6.7.5 give 0.6.7.2-5p, used both in the push-preparation commit's message title and in CHANGELOG. The short form is used only when the first and last commit share a prefix; with mixed number series both numbers are written in full (0.6.6.5.11-0.6.0.1p). The span is unambiguous in CHANGELOG: it is all the commit entries above the previous p-entry. The push entry is a separate CHANGELOG entry (directly above the commit entries) that owns the FINDINGS from the preparation: what was wrong, how it was discovered and how it was fixed - detailed enough to learn from, never just «findings fixed». That build, tests and validation were run and were green must not be there, however (see Routine verification under Writing style); only deviations from the ritual are logged. The commit entries describe what was built; the sequence of events from the review is only in the p-entry, so the two never drift apart. Releases carry the phase's minor with a running patch number (0.7.1, 0.7.2, ...), independent of the milestone numbers in the backlog; the phase release at the gate is simply the last of them (decided 15 September 2026; the engine field is strict three-part semver). This is how a piece of work is built in numbered commits and pushed to testing only when the whole is finished.
- **Done criteria:** new backlog milestones get a «Ferdig når:» (done when) line with observable conditions, and roadmap phases have a corresponding «Port:» (gate) line. «Works» is not a criterion; write what can be observed.
- **An answer to a question ends the turn.** Never open a choice dialog in the same turn as an explanation (the dialog hides the text); ask the follow-up question in plain text instead.
- **If the user's message ends with a question, the turn is pure discussion** (rule set 3 August 2026): answer in text and make no changes, even if the message also contains a go-ahead for something else. Changes are made only when the message is a pure directive without open questions.
- **Rule text is previewed** (rule set 3 August 2026): new or changed rules in this file are presented as a draft in the chat for approval before they are written in.

## Writing style

- **Never an em dash anywhere**: not in project text, code, comments, commit messages or chat replies. Use a plain hyphen or rephrase.
- **No person attributions in project text, CHANGELOG included** (rule tightened 9 August 2026): the log documents WHAT was done, never who wanted, chose or found it. Phrasings such as «eiers ønske/krav/funn», «eierbeslutning», «eiervalg», «eieren valgte» and «bestått av eieren» (and their English equivalents: «owner decision», «the owner chose») are written as impersonal, preferably dated facts («valgt 9. august 2026», «testfunn», «besluttet under klargjøringen», «bestått 9. august 2026»). Allowed are only the product role «the owner/site owner» (the person who owns the WEBSITE, in feature descriptions: «the owner pastes coordinates») and the ownership verb («BACKLOG.md owns the tasks», file ownership).
- **CHANGELOG records only real events**: actual fixes (what was wrong, how it was discovered, how it was fixed). Disproved assumptions, the agent's own misunderstandings and «clarifications» where nothing was done never go in - they are dropped silently.
- **CHANGELOG entries are short: what was wrong, and what was done** (rule set 9 August 2026): one bullet per change, one to two sentences. The symptom and the action must be there, so a reader sees what was actually done to fix a bug or build something. The rationale, the mechanics and the background belong in the code comment, SCHEMA.md or the ADR, and are pointed to by file name instead of being repeated. If a bullet explains WHY the action works, it is too long.
- **Routine verification is not logged** (rule set 9 August 2026): that build, tests and schema validation were run and were green is not a change, and must not appear in CHANGELOG. What must appear is outcomes: what a review FOUND and what was done about it, findings that turned out to be already solved and were therefore closed without a code change, and deviations from the ritual (e.g. that the review step had to be replaced by mechanical checks).
- **All text in code is English** (rule set 30 August 2026): comments, strings, error and console messages, test names, identifiers and data-contract values (block types, preset ids, translation keys, manifest fields) are written in English. Norwegian exists in only three places: the language dictionaries (locales), documents and log entries not yet translated (see the language rule below) and site content (content/, seed texts, and test data that is deliberately Norwegian content). User-visible text always goes through a translation key with an English fallback literal, never through a Norwegian literal in code. File and folder paths in user repos (content/samlinger/, content/maler/ and page slugs) are user data and keep their names; see ADR-0021.
- **English is the canonical language of Urd, Norwegian (bokmål) the secondary** (decided 11 September 2026, ADR-0022): everything developer-facing is written in English: code text (ADR-0021), this file, the ADRs, the documents under docs/, and new entries in CHANGELOG, BACKLOG and TESTRUNDER as well as commit messages (older entries stay as written). Documents not yet translated (VISJON, VEIKART, UTVIKLING, sammenligning/, CONTRIBUTING, BACKLOG, TESTRUNDER) stay in Norwegian until their turn, and the English text applies on discrepancy. Everything a site owner or visitor may read is available in both English and Norwegian: the README, the user guide and the setup guide under docs/languages/, and the UI texts (five languages, ADR-0012, with the bokmål dictionary as the base a missing key falls back to, and full parity for en-GB and tr). Outward-facing names are English: the README root files and the GitHub topics (`urd-template`, `urd-plugin`).
- **No emoji or characters in the editor UI: only drawn SVG icons.** (Characters and emoji are content the user may set, not chrome.)
- **No explanatory prose in the admin panels** (rule set 23 July 2026): settings are explained in «?» tooltips (the title attribute) or the help chip, never as text paragraphs (panel-hint and the like) in the panel. Settings that apply only to one variant or choice must sit DIRECTLY UNDER the choice they belong to.
- **Settings are shown ONLY when they are relevant** (rule set 23 July 2026): a choice that has no effect with the current variant or style must be hidden, not left inert (e.g. the effect colour only for hover styles with an effect, column choices only for side-by-side). The label must say what the setting actually controls in that choice («Glow colour» for lift with glow, not a generic «Hover colour»), and option lists are filtered to the variants that make sense.
- **Code comments wrap at sentence boundaries, never mid-sentence.** Match the surrounding code in comment density, naming and idiom.
- **Code comments describe, they do not correct** (rule set 11 August 2026): a comment says what the code does. Fix narratives never belong in a source file: what was wrong before, what an earlier attempt did, what «would otherwise happen», or that something is «no longer» so. The sequence of events is owned by CHANGELOG, and a finding from a review is written there, not in the file. Contrast form is allowed when it describes the choice («coloured text with an underline, not a filled pill»), but not when it describes history («no longer flex: 1»).

## Engine lessons (recurring pitfalls)

- **postMessage: NEVER send a `$state` proxy** (gives DataCloneError). Always use `$state.snapshot(...)`.
- **Id generation:** `crypto.randomUUID` does not exist on insecure origins (e.g. `http://0.0.0.0`, the local test server). Use `crypto.getRandomValues` (works everywhere). See `makeId` in `sections/presets.js`.
- **Themed UI (ADR-0009): never a native `<select>` in editing UI** (the popup follows the OS theme and becomes unreadable). Use `Dropdown.svelte` (admin), `createDropdown` (the engine's `dropdown.js` on the canvas, `/assets/urd/dropdown.js` from plugins), or segment buttons.
- **Help chip (ADR-0008): everything with special functions must have a «?» chip** that opens a persistent help card. Shared helper: `attachHint` (the engine's `hint.js`; plugins import `/assets/urd/hint.js`).
- **Auto-grow changes the display only, never the frame** (ADR-0024): a block whose content is taller than its frame grows its own box, and the push pass in render.js moves the blocks below; the measured height is never written into `frames.desktop.h` (that hid the growth from the push in the preview). Plugin copies may still post `urd-grow` with ONLY the height, never the whole frame, otherwise a dragged block is teleported back.
- **Sections MUST have an `id`.** `handleAddSection` assigns one defensively if a preset forgets it.
- **Local development must work** (`python3 dev-server.py` from the repo root; `python3 -m http.server` caches engine files and does not route the page registry): plugin developers work locally. Things that only work on the deployed site (functions) must degrade gracefully locally.
- **Hover UI must be guarded against hybrid devices:** `pointerenter` also fires on a tap on a laptop with a touchscreen, so without an `event.pointerType === 'mouse'` guard a hover element opens and closes in the same tap. See the hover handling in `engine/nav.js`.
- **Engine components that re-render per draft message and set listeners on document must detach the previous set** (otherwise the listeners stack up for every editor change). The pattern: a module-level AbortController that is aborted at the top of the render function, and `{ signal }` on every addEventListener. See `renderNav` in `engine/nav.js`.
- **Build components native/CSS-first (ADR-0011):** use browser primitives over custom JS - `<dialog>`/`showModal()` for modal and lightbox, `<details name>` for accordion, `animation-timeline: view()` for scroll-linked effects (parallax), the Popover API for menus where anchoring exists. Gate everything that is not baseline with `@supports` or a feature check; fallback = either a JS path or the element in its END STATE (never hidden). `IntersectionObserver`/`ResizeObserver` are still right for LOGIC (one-off reveal, resize), not for scroll animation - one-off entrance therefore stays on IntersectionObserver.
- **Plugins import ONLY `/assets/urd/` paths** (i18n, hint, dropdown): the engine lives in a versioned, immutable-cached directory that is swapped at every release, so a hard-coded versioned path breaks at the next update. Shells and engine end up on the same module URL, so the i18n registries remain singletons (ADR-0013).
- **New error codes in functions require `api.<code>` keys in all five admin dictionaries** (the contract test in tests/i18n.test.mjs enforces it). Functions never have locale infrastructure: the English `error` text is the fallback, the client translates with `taApiError` and NEVER compares against literals.
- **New UI keys go into the core languages nb, en-GB and tr with {var} parity** (the parity test enforces full parity for the three; nn and se fall back to bokmål and are filled in dedicated translation rounds; the test accepts gaps but never unknown keys). The admin dictionaries are never bundled, so translations do not require a rebuild. `ta()` is never called at module level, and seed text (user data) is translated ONCE on insertion, never on render (ADR-0012).
- **New engine modules are kept OUTSIDE the static import closure** unless every visitor needs them: the modulepreload test forces the whole closure into the HTML shells. Rarely used code is loaded dynamically with an absolute `/assets/urd/` path + `/* @vite-ignore */`.
- **The slug copies must be byte-identical to the root index.html** (the copy-refresh duty): any mechanism that swaps the engine version writes the root + all copies in the same commit (ADR-0013; the modulepreload test guards it).

## Plugins

The reference plugins in `template/plugins/` (calendar, form, map, and the language pack lang-sv) show the pattern: a manifest with `provides` (optional for pure language packs with the `languages` field), a block with `version`/`migrations`, a section preset (with `id`), own CSS via ONE style tag, editing in the preview via `urd-edit`, a help chip, themed dropdowns, imports only from `/assets/urd/`, multilingual via the `locales`/`names` fields, and pure logic in its own module with `node --test` tests. Shared in its own repo with the GitHub topic `urd-plugin`. See `template/plugins/README.md`.

## The test rounds (docs/TESTRUNDER.md)

`docs/TESTRUNDER.md` is the checklist of delivered work awaiting manual testing (moved out of the backlog 22 July 2026). On delivery: add a new «Testrunde-batch (0.6.9.x)» section at the top there (batches may be merged when asked). **Add new items when you deliver something, but never remove anything there; items are struck only by whoever tests.**

## Running tools

Run node and npm the way your environment requires. On the original development machine, host commands run via `flatpak-spawn --host` (Flatpak sandbox); on an ordinary machine you run them directly.
